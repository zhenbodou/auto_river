# 8.5 运行时工程：背压、可观测性与资源预算

节点“都能跑”离可长期上车还有很远。系统工程师必须能解释数据为何新鲜、队列为何不会爆、故障如何定位、资源争用如何受控。

## 队列是一种延迟债务

生产者快于消费者时，无界队列不会解决问题，只会把内存和延迟推到未来。对周期传感器流，旧帧通常没有价值，应使用有界队列并显式选择：

- **drop oldest**：保最新数据，适合相机/点云到感知；
- **drop newest**：保护正在处理的序列，适合不可跳步的状态机；
- **block/backpressure**：适合离线管线，不一定适合实时传感器；
- **coalesce**：配置/状态只保留最新值。

Little 定律 $L=\lambda W$ 给出直觉：30 Hz 输入、队列平均 3 帧，仅排队就约 100 ms。每条边必须写清容量、溢出策略和过期时间。

## Deadline、freshness 与端到端追踪

消息头同时保留采集时间、发布/接收时间、sequence 和 trace ID。模块要区分：计算慢、排队慢、网络慢、输入本来就旧。接收端在使用前检查 freshness；过期轨迹即使数值正确也不能下发控制。

端到端 trace 应能串起“某个控制命令由哪些传感器帧产生”，并记录每段耗时。日志只告诉你发生了什么，指标告诉你是否普遍，trace 告诉你时间花在哪。

## 三类可观测信号

- **Metrics**：频率、p99 延迟、队列深度、丢帧、deadline miss、CPU/GPU/内存、传感器健康。
- **Logs**：结构化字段包含 node、frame/trace ID、错误类别和状态转换；热路径限流。
- **Traces**：跨节点 span，采样但保留所有故障/超时链路。

报警必须可行动，例如“规划输入 age p99 > 150 ms 持续 5 s”，而不是“CPU 有点高”。

## 资源隔离与调度

先做端到端预算，再设置线程数、优先级、CPU affinity、内存上限和 GPU stream。避免每个节点都建立“CPU 核数个线程”的运行时造成过度订阅。关键控制线程与日志压缩、上传、可视化隔离；验证优先级反转和共享锁。

在目标硬件、热稳态、真实输入峰值下测量。桌面工作站平均结果不能替代车规 SoC 上的 p99/WCET 证据。

## 启停、配置与故障语义

节点生命周期至少包含 `Unconfigured → Inactive → Active → Degraded/Fault`。启动要有依赖就绪条件；停止要先阻断新输入、排空或丢弃队列、释放硬件；重启不能把旧消息当新消息。

配置必须 schema 校验、版本化、可回滚；动态参数区分“安全在线可改”和“必须停车重启”。一次配置变更要能关联到指标变化。

## 混沌与故障注入

注入丢包、乱序、延迟、时钟跳变、节点 crash、CPU 压力、磁盘满和 GPU 超时，检查：故障被检测的时间、错误传播范围、降级状态、恢复条件和证据是否完整。正常路径测试无法证明系统在坏天气里有秩序地坏掉。

## 本章验收

把第 10.1 节最小栈改成有界通道；分别制造生产者过载和规划卡顿；画出队列深度与数据 age；实现 drop/过期策略和 trace ID；证明内存有界、控制永不使用过期轨迹，并提交一次节点崩溃的恢复时间线。

## 小结

- 每条队列都需要容量、溢出策略和 freshness 契约。
- 可观测性应贯穿端到端因果链，并直接服务于报警和调试。
- 资源隔离、生命周期、配置治理和故障注入决定系统是否可运营。
