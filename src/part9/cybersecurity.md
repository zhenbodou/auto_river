# 9.4 汽车网络安全、供应链与安全 OTA

功能安全问“随机故障或设计不足会不会伤人”，网络安全问“攻击者能否让它伤人”。联网车辆的诊断口、传感器网络、OTA、云端和依赖供应链都在攻击面内。

## 从资产和信任边界开始

先列资产：控制权限、软件/模型、标定、密钥、定位与用户数据、日志。再画信任边界：车内安全域与信息娱乐域、车—云、ECU—传感器、诊断设备、开发/发布系统。

对每条数据流做威胁分析：伪造、篡改、抵赖、信息泄露、拒绝服务、权限提升。风险不能只按“容易攻击”排序，还要结合车辆影响和暴露时间。

## 深度防御

- 网络分区与最小权限；安全网关限制跨域消息和速率。
- 相互认证、加密与防重放；密钥存入硬件安全模块并可轮换。
- Secure Boot/Measured Boot 验证启动链；运行时限制调试与不必要服务。
- 消息做范围、频率、状态一致性检查；“通过认证”不等于“语义安全”。
- 安全监控记录异常但避免泄露秘密，并准备车端安全降级。

控制网络遇到洪泛时，策略不是无限重试，而是保证关键控制流带宽、隔离攻击源，并按安全分析进入 MRM。

## Rust 依赖供应链

锁定依赖并审核更新；生成 SBOM；检查已知漏洞、许可证、构建脚本、过程宏和 `unsafe`；最小化 features；发布构建在受控环境产生可追溯制品。`Cargo.lock` 保证解析一致，不等于依赖可信。

安全门禁至少包含：`cargo audit`/组织漏洞源、许可证策略、恶意包/来源审查、secret 扫描、制品哈希与签名。对暂不修复漏洞记录可利用性分析、缓解措施、负责人和截止日期。

## 安全 OTA 是一个状态机

可靠 OTA 流程：生成并签名 manifest → 车辆校验身份/车型/版本/依赖 → 下载并验证哈希 → 写入非活动分区 → 重启健康检查 → 成功提交或自动回滚。

必须防止：降级到有漏洞旧版本、断电变砖、密钥泄露后无法吊销、模型与运行时不兼容、部分 ECU 版本组合非法。A/B 分区、anti-rollback counter、分批灰度和 kill switch 都应在设计中明确。

## 漏洞响应

上线不是结束。需要漏洞接收渠道、车队影响查询、修复优先级、签名发布、灰度观察、回滚和监管/用户沟通流程。日志与 SBOM 要能回答“哪些 VIN 使用了受影响版本”。

## 标准边界

ISO/SAE 21434 提供道路车辆网络安全工程生命周期框架；法规和组织流程还可能要求网络安全管理与软件更新管理。本章是工程导览，不替代组织合规、法律意见或标准原文。

## 本章验收

为“云端下发模型到感知 ECU”画数据流和信任边界，给出至少 10 个威胁、风险与缓解；设计 A/B OTA 状态机，逐项测试断电、签名错误、版本不兼容、健康检查失败和回滚；输出一份 SBOM 与依赖例外清单。

## 小结

- 网络安全要从资产、信任边界和可追踪威胁开始，而不是最后补 TLS。
- 车端防御必须与安全降级、资源保护结合。
- OTA 和供应链需要签名、可追溯、灰度、回滚及持续漏洞响应。

延伸阅读：[ISO/SAE 21434 标准页面](https://www.iso.org/standard/70918.html)。
