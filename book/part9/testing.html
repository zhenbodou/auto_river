Rust 智能驾驶开发：从小白到工程师

9.2 测试策略：单元、集成与录制回放

上一节你学会了怎么造一个"虚拟世界"来跑算法。但"能跑"和"跑对"是两回事。这一节回答的问题是：在一个由几十个模块、几十万行代码、还得在物理世界里赌上人命的系统里，你怎么用工程手段建立起"它是对的"这份信心？

这一节是整个第九部分里 Rust 工程性最强的一章。我会带你从最基础的 #[test] 一路走到自动驾驶测试真正的王牌——录制回放测试。Rust 在这里有个别的语言羡慕不来的优势：测试是语言的一等公民，cargo test 开箱即用，不需要任何第三方框架就能写出工业级的测试。我们会把这个优势吃干榨净。

自动驾驶的测试金字塔长什么样

软件工程里有个经典的"测试金字塔"（test pyramid）：底部是大量快、便宜、隔离的单元测试，往上是数量递减、越来越慢越来越贵的集成测试和端到端测试。自动驾驶也是这个形状，但每一层都有它的行业特色：

                  ▲  贵、慢、少
        ┌─────────────────────┐
        │   真车 / 封闭场地测试  │   最终验证，成本极高
        ├─────────────────────┤
        │  闭环仿真场景测试(SIL)  │   造长尾、测决策连锁反应
        ├─────────────────────┤
        │   录制回放回归测试      │   ★自动驾驶的核心★ 海量真实数据
        ├─────────────────────┤
        │      集成测试         │   多模块拼接：感知→预测→规划
        ├─────────────────────┤
        │      单元测试         │   单个函数：一次坐标变换、一步滤波
        └─────────────────────┘
                  ▼  便宜、快、多

和普通后端系统最大的不同，是中间那两层特别厚：录制回放和仿真场景。因为自动驾驶的正确性高度依赖"面对真实世界的复杂分布时表现如何"，这是任何单元测试都覆盖不到的。但别因此轻视底层——金字塔底座越宽，上层排查问题就越省力。一个坐标变换的 bug，你是希望在一个 0.1 毫秒的单元测试里抓到，还是在一次跑了半小时的仿真里发现指标莫名其妙变差、再花一天去定位？

Rust 单元测试：从零件开始建立信心

Rust 的单元测试就写在被测代码同一个文件里，用一个带 #[cfg(test)] 的模块包起来。#[cfg(test)] 的意思是"只在 cargo test 时编译这段"，正式构建里它不存在、不占一丁点体积——这对车载这种资源受限环境很友好。

给自动驾驶写单元测试，最值钱的靶子是那些纯函数式的数学/几何计算：坐标变换、角度归一化、滤波器的一步更新、控制律的一次求解。它们输入输出明确、无副作用，最好测。

先看一个几何函数和它的测试。假设我们有一个"把点从世界坐标系变到车体坐标系"的函数——这是感知里天天用的操作：

#![allow(unused)]
fn main() {
/// 把世界系下的点 (wx, wy) 变换到车体系。
/// 车体在世界系的位姿是 (px, py, ptheta)。
/// 车体系：x 朝车头，y 朝车左。
pub fn world_to_body(wx: f64, wy: f64, px: f64, py: f64, ptheta: f64) -> (f64, f64) {
    let dx = wx - px;
    let dy = wy - py;
    let c = ptheta.cos();
    let s = ptheta.sin();
    // 旋转 -ptheta（即世界到车体的逆旋转）
    let bx = c * dx + s * dy;
    let by = -s * dx + c * dy;
    (bx, by)
}

#[cfg(test)]
mod tests {
    use super::*;

    // 一个好用的浮点近似断言。浮点数几乎永远不该用 == 比较，
    // 因为 cos/sin 会引入微小舍入误差。
    fn approx(a: f64, b: f64) -> bool {
        (a - b).abs() < 1e-9
    }

    #[test]
    fn 车体在原点无旋转时_世界系就是车体系() {
        let (bx, by) = world_to_body(3.0, 4.0, 0.0, 0.0, 0.0);
        assert!(approx(bx, 3.0));
        assert!(approx(by, 4.0));
    }

    #[test]
    fn 车头朝北时正前方的点应落在车体x轴() {
        // 车在原点，朝向 +90°（车头指向世界 +y）。
        // 世界系正上方的点 (0, 5)，在车体系里应该是"正前方 5 米"。
        let theta = std::f64::consts::FRAC_PI_2;
        let (bx, by) = world_to_body(0.0, 5.0, 0.0, 0.0, theta);
        assert!(approx(bx, 5.0), "车体系纵向应为 5，实际 {}", bx);
        assert!(approx(by, 0.0), "车体系横向应为 0，实际 {}", by);
    }

    #[test]
    fn 平移不影响相对几何() {
        // 车挪到 (100, 100)，点也同步挪 (100, 100)，相对关系不变。
        let (bx, by) = world_to_body(103.0, 104.0, 100.0, 100.0, 0.0);
        assert!(approx(bx, 3.0));
        assert!(approx(by, 4.0));
    }
}
}

几个地道 Rust 测试的要点，请当成习惯记下来：

  • assert! / assert_eq! / assert_ne! 是三个主力宏。assert_eq!(a, b) 失败时会自动打印出 a 和 b 的实际值，比 assert!(a == b) 好用得多——排错时你想看到"期望 5.0，实际得到 4.997"，而不是干巴巴一个"false"。
  • 浮点绝对不要用 ==。上面那个 approx 辅助函数（或用 float-cmp、approx 这类 crate）是几何计算测试的标配。cos(π/2) 在计算机里不是精确的 0，而是 6.12e-17 这种东西。
  • 测试函数名可以用中文，而且应该写成一句人话——它就是一句可执行的规格说明。车头朝北时正前方的点应落在车体x轴 比 test_transform_2 强一百倍：测试挂了的时候，光看名字你就知道哪条性质被破坏了。
  • 给 assert! 加上失败信息（第二个参数），把实际值打出来，能省你大量重跑调试的时间。

再看一个更"自动驾驶"的例子：给一个纯纵向的 PID 控制器写测试。控制器这种带状态、带反馈的东西，测的是它的行为性质，而不是某个具体数值：

#![allow(unused)]
fn main() {
pub struct Pid {
    kp: f64,
    ki: f64,
    kd: f64,
    integral: f64,
    prev_err: f64,
}

impl Pid {
    pub fn new(kp: f64, ki: f64, kd: f64) -> Self {
        Self { kp, ki, kd, integral: 0.0, prev_err: 0.0 }
    }

    /// 输入期望值与当前值，输出控制量。dt 为时间步。
    pub fn update(&mut self, setpoint: f64, measured: f64, dt: f64) -> f64 {
        let err = setpoint - measured;
        self.integral += err * dt;
        let deriv = (err - self.prev_err) / dt;
        self.prev_err = err;
        self.kp * err + self.ki * self.integral + self.kd * deriv
    }
}

#[cfg(test)]
mod pid_tests {
    use super::*;

    #[test]
    fn 误差为正时应输出正的控制量_让被控量往上追() {
        let mut pid = Pid::new(1.0, 0.0, 0.0);
        // 期望 10，当前 0，误差 +10，纯比例应输出 +10。
        let u = pid.update(10.0, 0.0, 0.1);
        assert!(u > 0.0, "期望正输出，实际 {}", u);
    }

    #[test]
    fn 闭环仿真下应收敛到设定值() {
        // 把 PID 接到一个最简单的一阶被控对象上跑闭环，
        // 验证它最终能把状态稳到设定值附近——这是控制器最核心的性质。
        let mut pid = Pid::new(0.8, 0.2, 0.05);
        let mut x = 0.0;         // 被控量，从 0 起
        let setpoint = 5.0;
        let dt = 0.05;
        for _ in 0..1000 {
            let u = pid.update(setpoint, x, dt);
            x += u * dt;         // 极简一阶模型：状态被控制量推动
        }
        assert!((x - setpoint).abs() < 0.05, "未收敛，最终 x = {}", x);
    }
}
}

注意第二个测试的思路：我们不去断言"第 37 步的输出必须是 3.14159"（那种测试又脆又没意义，改个增益就红），而是断言一个行为契约——"这个控制器闭环下必须收敛到设定值"。这才是测控制器的正确姿势：测性质，别测魔法数字。

面试题："你会怎么给一个卡尔曼滤波器写单元测试？" 弱回答是"喂一组数据看输出对不对"。强回答会分层：① 测不变量——协方差矩阵必须始终对称、正定；② 测极限行为——测量噪声设为 0 时估计应完全信任测量，设为无穷大时应完全信任预测；③ 测收敛性——喂一个恒定真值加噪声，估计的方差应随时间下降并收敛。能说出"测不变量和极限行为"，就说明你懂怎么测有状态的数值算法。

集成测试：把模块拼起来测

单元测试测的是"零件"，集成测试测的是"零件拼在一起对不对"。Rust 对集成测试有专门约定：放在项目根目录的 tests/ 文件夹里，每个文件是一个独立的测试 crate，只能调用你的 pub 接口——这恰好模拟了"外部使用者"的视角，逼你把模块边界设计干净。

对自动驾驶，一个典型的集成测试是把感知输出 → 预测 → 规划串起来，喂一个构造好的场景，验证整条链路的输出合理：

// tests/planning_pipeline.rs
use my_av_stack::perception::Obstacle;
use my_av_stack::prediction::predict_trajectories;
use my_av_stack::planning::plan_trajectory;

#[test]
fn 前方静止障碍物时规划应减速或绕行() {
    // 构造一个场景：正前方 15 米有一辆静止的车。
    let obstacles = vec![Obstacle {
        id: 1,
        x: 15.0, y: 0.0,
        vx: 0.0, vy: 0.0,
        // ... 其余字段
    }];

    // 跑预测：静止车预测轨迹应基本原地不动。
    let predictions = predict_trajectories(&obstacles);

    // 跑规划：自车当前 10 m/s 直行。
    let ego_v = 10.0;
    let traj = plan_trajectory(ego_v, &predictions);

    // 契约级断言：规划出的轨迹不能撞上那辆车。
    // 我们不关心具体怎么绕，只关心"安全"这个不可谈判的性质。
    let min_dist = traj.points.iter()
        .map(|p| (p.x - 15.0).hypot(p.y - 0.0))
        .fold(f64::INFINITY, f64::min);
    assert!(min_dist > 2.0, "轨迹逼近障碍物到 {:.2}m，不安全", min_dist);

    // 且末端速度应低于初速——要么刹停要么减速绕行。
    let end_v = traj.points.last().unwrap().v;
    assert!(end_v < ego_v, "面对前方障碍未减速，末速 {:.2}", end_v);
}

集成测试的哲学和单元测试一脉相承：断言不可谈判的安全性质（不能撞、要减速），而不是某条具体轨迹。因为"怎么绕"是可以随算法优化变的，"不能撞"永远不能变。你的测试应该锁住后者、放开前者，否则每次算法改进都伴随一堆测试变红，团队很快就会习惯性地无视测试——那是最坏的结局。

基于属性的测试：让机器帮你找反例

单元测试有个根本局限：你只能测你想得到的用例。但 bug 往往藏在你没想到的输入里——负的角度、超过 2π 的朝向、恰好在坐标轴上的退化情形。基于属性的测试（property-based testing，PBT）换了个思路：你不写"输入 3 得到 5"，而是声明一条对所有输入都该成立的性质，然后让框架随机生成成千上万个输入去试图证伪它。找到反例，它还会自动缩小（shrink）到最简的那个，直接甩你脸上。

Rust 里最常用的是 proptest。加依赖：

# Cargo.toml
[dev-dependencies]
proptest = "1"

自动驾驶里 PBT 的黄金应用场景是坐标变换的往返等价（round-trip）——一个变换和它的逆，复合起来必须等于恒等。这是几何代码正确性的基石，而它天然适合表达成"对所有点都成立的性质"：

use proptest::prelude::*;

/// 车体系变回世界系（world_to_body 的逆）。
fn body_to_world(bx: f64, by: f64, px: f64, py: f64, ptheta: f64) -> (f64, f64) {
    let c = ptheta.cos();
    let s = ptheta.sin();
    let wx = c * bx - s * by + px;
    let wy = s * bx + c * by + py;
    (wx, wy)
}

proptest! {
    #[test]
    fn 世界到车体再变回来应回到原点(
        // 让 proptest 在合理范围内随机生成这些值，跑 256 组（默认）
        wx in -1000.0f64..1000.0,
        wy in -1000.0f64..1000.0,
        px in -1000.0f64..1000.0,
        py in -1000.0f64..1000.0,
        ptheta in -10.0f64..10.0,   // 故意超出 [-pi, pi]，试探角度处理
    ) {
        let (bx, by) = world_to_body(wx, wy, px, py, ptheta);
        let (wx2, wy2) = body_to_world(bx, by, px, py, ptheta);
        // 往返后必须回到原点（容忍浮点误差）。
        prop_assert!((wx - wx2).abs() < 1e-6, "x 往返失配: {} vs {}", wx, wx2);
        prop_assert!((wy - wy2).abs() < 1e-6, "y 往返失配: {} vs {}", wy, wy2);
    }
}

这一个测试，等价于你手写几千个坐标点用例——而且是你根本想不到要写的那些（比如 ptheta = 9.9 这种超出常规范围的角度）。如果你的变换里藏着一个符号错误或角度归一化 bug，proptest 几乎必然会揪出来，并告诉你"当输入是 (0, 1, 0, 0, 3.14159...) 时失败"这样一个最小反例。

PBT 特别适合表达的自动驾驶不变量还有很多，列几个让你有感觉：

  • 控制器不变量：饱和后的输出永远在 [-max, max] 范围内，无论输入多离谱。
  • 角度归一化：normalize_angle 的输出永远落在 (-π, π]，且对已经在范围内的输入是恒等的。
  • 滤波器数值健康：无论喂什么合法观测，协方差矩阵始终保持对称。
  • 轨迹的物理合理性：规划出的轨迹，相邻点的加速度永远不超过车辆物理上限。
proptest! {
    #[test]
    fn 归一化后的角度必落在正负pi区间(a in -1000.0f64..1000.0) {
        let n = normalize_angle(a);
        prop_assert!(n > -std::f64::consts::PI - 1e-9);
        prop_assert!(n <= std::f64::consts::PI + 1e-9);
    }
}

中高级视角：PBT 不是要取代单元测试，而是补上它的盲区。单元测试擅长锁定具体的、你已知的关键案例（"这个 CVE 场景必须处理对"）；PBT 擅长在广阔的输入空间里扫雷，找你没想到的退化情形。几何和数值密集的自动驾驶代码，两者都该有。会用 proptest 测往返等价，是一个能立刻让面试官高看你的技能点。

录制回放测试：自动驾驶测试的王牌

现在讲最重要的。前面所有测试都有一个共同的软肋：它们只能验证你想象中的世界。可自动驾驶的真正敌人是真实世界的复杂分布——那些你在办公室里永远编不出来的光影、遮挡、加塞、鬼探头。

录制回放测试（replay test / regression test）就是把 9.1 节讲的 record & replay 变成自动化测试：用真实（或高质量仿真）采集的数据，作为回归测试的输入，确保你今天的改动没有把昨天修好的东西改坏。 这是自动驾驶测试的核心，没有之一。

它的机制是这样的：

  1. 积累回放集。车队跑出来的数据里，那些难例（disengagement 现场、系统曾经犯错的片段、罕见构型）被挑出来，连同期望输出（人工标注的真值，或经过审核的正确结果），存成一批带时间戳的用例（就是 9.1 里的 mcap 片段）。
  2. 回放喂给算法。测试时，逐个用例把传感器数据按序喂给你的算法当前版本，收集它的输出。
  3. 和期望比对，算指标。逐帧对比"算法这次的输出"和"期望输出"，算出一组指标：感知的检测召回率/误检率、跟踪 ID 是否稳定、规划轨迹和人类驾驶的偏差……
  4. 卡阈值。任何一个关键指标相比基线退化超过阈值，测试失败，这个改动就不许合入。

这套东西，就是你手边 inf/ 那套流水线的使命。它把一批 testcase 批量喂给模型跑推理、产出结构化结果（describe.json / messages.json 那类），再转成统一格式（cvproto）交给评测环节打分。这不是玩具，这是数据闭环里"离线推理 + 评测"那一环的工业级引擎——是每天在 CI 里守着"改代码别改坏感知"这条防线的哨兵。

用 Rust 搭一个最小的录制回放测试骨架，让你看清它的结构：

// tests/replay_regression.rs
use std::path::Path;

/// 一个回放用例：一段真实数据 + 它的期望输出（真值）。
struct ReplayCase {
    name: &'static str,
    log_path: &'static str,       // mcap 文件路径
    baseline_metric: f64,          // 上一版本达到的指标（基线）
    tolerance: f64,                // 允许退化的容差
}

/// 跑一个用例：回放数据、过算法、算指标。（此处为骨架，实际调用你的栈）
fn run_case(case: &ReplayCase) -> f64 {
    let frames = load_mcap(Path::new(case.log_path));   // 8.4 节的 mcap 读取
    let mut hits = 0usize;
    let mut total = 0usize;
    for frame in frames {
        // 把这一帧的传感器数据喂给被测算法
        let output = my_av_stack::perception::detect(&frame.sensor_data);
        // 和这一帧标注的真值比对，累计命中
        let (h, t) = evaluate_frame(&output, &frame.ground_truth);
        hits += h;
        total += t;
    }
    hits as f64 / total.max(1) as f64   // 例如：检测召回率
}

#[test]
fn 感知在关键难例集上不得退化() {
    let cases = [
        ReplayCase {
            name: "雨天逆光十字路口",
            log_path: "testdata/rainy_intersection.mcap",
            baseline_metric: 0.92,
            tolerance: 0.02,
        },
        ReplayCase {
            name: "隧道口强明暗变化",
            log_path: "testdata/tunnel_exit.mcap",
            baseline_metric: 0.88,
            tolerance: 0.02,
        },
    ];

    for case in &cases {
        let metric = run_case(case);
        // 关键：只允许在容差内退化，否则这次改动就是回归，必须拦下。
        assert!(
            metric >= case.baseline_metric - case.tolerance,
            "用例[{}]召回率退化: 基线 {:.3}, 本次 {:.3}",
            case.name, case.baseline_metric, metric,
        );
    }
}

请体会这套设计的几个关键点：

  • 基线 + 容差，而不是精确相等。感知/规划这种复杂系统，指标不可能每次一模一样（浮点、并行顺序都会造成微小抖动）。你锁的是"不许比上一版明显变差"，而不是"必须一字不差"。
  • 它测的是分布，不是个例。一个覆盖了几千个真实难例的回放集，捕捉退化的能力远超任何手写单元测试——因为它面对的是真实世界的样本，而不是你办公室里的想象。
  • 它是数据闭环的闭合点。车队采数据 → 挖难例 → 进回放集 → 每次提交都回归 → 发现退化 → 修 → 再进回放集。系统就是这样越测越强的。

真实项目里：一个成熟自动驾驶团队的 CI，每次合并请求都会触发几千到几万个片段的回放回归，可能跑在一个大集群上要几十分钟到几小时。这套基础设施的效率——回放跑多快、指标算多准、退化定位多方便——直接决定了团队的迭代速度。这正是 Rust 大展身手的地方：回放和评测是纯计算密集、要跑海量数据的离线任务，用 Rust 替掉原来的 Python 脚本，能拿到成倍的吞吐和确定性。你手边的 inf/ 就是这条路径的真实产物。

场景测试与指标：怎么给"开得好不好"打分

回放测试擅长感知/预测这种有明确真值的模块。但规划/控制的"好不好"没有唯一正确答案（一个路口有一百种合理的过法）。这时用闭环仿真场景测试：在 9.1 的仿真里放一个场景，让完整的自车栈去开，然后用一组指标给这次驾驶打分。核心指标分三大类，你要背下来：

  • 安全（safety）：有没有碰撞（collision）？和其他物体的最小距离、最小 TTC（time-to-collision，碰撞时间）够不够？有没有闯出车道、逆行？——这类是红线，破了就是失败，不容妥协。
  • 舒适（comfort）：加速度、加加速度（jerk，加速度的变化率）超没超过舒适阈值？急刹急打方向都会让乘客难受。一个不撞车但一路点头哈腰的系统，量产不了。
  • 交规与合理性（compliance & progress）：闯红灯没有？超速没有？该让行让了没有？以及——有没有把事办成（开到目的地了吗，还是怂在原地不敢动）？最后这条常被忽视：一个永远急刹不动的车"很安全"，但毫无用处。
#![allow(unused)]
fn main() {
/// 一次仿真跑完后，从轨迹历史里算出的评分。
struct DriveMetrics {
    collided: bool,          // 是否发生碰撞（红线）
    min_ttc: f64,            // 最小碰撞时间（秒）
    max_jerk: f64,           // 最大加加速度（舒适）
    ran_red_light: bool,     // 是否闯红灯（交规）
    reached_goal: bool,      // 是否到达目标（有效性）
}

#[test]
fn 直行遇前车急刹场景应安全停车且不追尾() {
    let scenario = Scenario::load("scenarios/lead_vehicle_hard_brake.yaml");
    // 在 9.1 的仿真器里跑完整自车栈，返回逐步历史
    let history = run_closed_loop(&scenario, /* steps */ 400);
    let m = evaluate_drive(&history);

    // 安全红线：绝不允许碰撞。
    assert!(!m.collided, "发生追尾碰撞！");
    // 安全裕度：全程 TTC 不得低于 1.5 秒。
    assert!(m.min_ttc > 1.5, "最小 TTC 仅 {:.2}s，过于危险", m.min_ttc);
    // 舒适：紧急场景允许较大 jerk，但仍设上限防止过激。
    assert!(m.max_jerk < 10.0, "加加速度 {:.1} 过大，乘客体验差", m.max_jerk);
    // 有效性：不能一慌就永远停着不动（此场景应停稳后择机恢复）。
    // ……视场景定义补充
}
}

覆盖率：代码覆盖率 vs 场景覆盖率

"我们测得够不够？"这个问题有两个完全不同的答案，别混为一谈：

  • 代码覆盖率（code coverage）：跑测试时，你的代码有百分之多少的行/分支被执行过。Rust 里可以用 cargo llvm-cov（基于 LLVM 的插桩）来测。它回答的是"我有没有哪段代码从没被测到"。有用，但有天花板。
  • 场景覆盖率（scenario coverage）：你的测试集覆盖了多少种真实世界的驾驶情形——各种天气、路口类型、交通参与者行为、极端构型。

关键洞见，也是自动驾驶测试的一句行话：代码覆盖率 100% 不代表系统安全，场景覆盖率才是自动驾驶真正要爬的山。 你的代码可能每一行都被执行过，但你的测试从没见过"暴雨夜里一个穿黑衣服的行人推着没开灯的自行车横穿"这种构型——而这恰恰是会出事的地方。代码覆盖率是软件工程的通用指标，场景覆盖率才是这个行业的命门，且永远不可能真正达到 100%（真实世界的情形是无穷的）。这也正是域随机化和自动场景生成存在的意义：尽可能扩大场景覆盖。

面试题："代码覆盖率和场景覆盖率有什么区别，哪个对自动驾驶更重要？" 能清楚区分二者、并指出"高代码覆盖率是必要不充分条件，场景覆盖率永远无法穷尽、是长尾问题的本质"，就是一个漂亮的回答。

CI 中的仿真回归

把上面这些串起来，就是一套现代自动驾驶的**持续集成（CI）**流程。每次有人提交代码，流水线自动跑：

  1. cargo build + cargo clippy：编译过、静态检查过（Rust 的 clippy 能抓一堆潜在问题）。
  2. cargo test：所有单元测试、集成测试、proptest 属性测试——秒级到分钟级，最快的一道闸门，跑不过直接打回。
  3. 录制回放回归：几千个真实片段过一遍，感知/预测指标不得退化——分钟级到小时级，可能跑在集群上。
  4. 闭环仿真场景套件：一批安全关键场景在仿真里跑闭环，安全指标不得破线。
  5. 全绿，才允许合入主干。

分层的意义是快速失败（fail fast）：便宜快的测试在前，贵慢的在后。一个坐标变换的低级错误，应该在第 2 步几秒内被 proptest 抓住，而不是耗到第 4 步跑了一小时仿真才发现。这就是为什么金字塔底座要宽。

确定性与可复现：一切测试的地基

最后讲一个贯穿所有测试、却最容易被新手忽视的东西：确定性（determinism）。

一个测试如果同样的输入，有时过有时不过（业界叫 flaky test，"薄脆测试"），那它比没有测试还糟——因为团队会开始不信任测试，红了就无脑重跑，直到某次真的 bug 也被当成"又抽风了"放过去。对赌人命的自动驾驶，这是绝对不能接受的。

自动驾驶里破坏确定性的元凶有几个，你要能一眼认出：

  • 随机数。感知里的采样、规划里的随机化搜索（如 RRT）、域随机化，全靠随机数。解法是固定随机种子（seed）——测试和回放时用同一个种子，随机序列就完全可复现。别让系统时间或 /dev/urandom 悄悄溜进你的算法。
  • 多线程调度的不确定性。几十个模块并行跑，消息到达顺序、锁的竞争结果每次都可能不同。回放测试里，一个常见做法是用确定性调度——不按真实墙上时钟（wall clock）驱动，而是用逻辑时钟按录制的时间戳严格排序地喂数据，让整个系统的执行顺序在每次回放里都完全一致。
  • 浮点的并行归约。多线程把一堆浮点数加起来，相加顺序不同，因舍入误差结果就有微小差异。要严格复现，得固定归约顺序，或用容差断言（这就是前面所有断言都用 < 1e-6 而不是 == 的深层原因之一）。

Rust 在这件事上帮了你大忙：它的所有权和借用系统在编译期就消灭了数据竞争（第 1.4 节讲过），这意味着你的并发代码不会因为"两个线程同时踩一块内存"而产生真正随机的、不可复现的垃圾结果。数据竞争是不确定性最恶劣的来源之一，而 Rust 直接把它挡在了门外。你仍然要管好随机种子和调度顺序，但至少最脏的那一类不确定性，编译器替你根除了。

// 好习惯：测试和回放里，随机数发生器永远用固定种子构造。
use rand::{SeedableRng, rngs::StdRng};

fn make_rng() -> StdRng {
    // 固定种子 = 每次运行随机序列完全一致 = 可复现。
    StdRng::seed_from_u64(42)
}

#[test]
fn 随机搜索规划器在固定种子下结果可复现() {
    let traj1 = plan_with_rng(&scenario(), &mut make_rng());
    let traj2 = plan_with_rng(&scenario(), &mut make_rng());
    // 同种子、同输入，必须得到逐字节一致的轨迹。
    assert_eq!(traj1, traj2, "规划器不可复现，测试将变得不可信");
}

中高级视角：确定性不只是为了测试好过，它是事故可复盘的前提。真车出了问题，你想在办公室里用录下的数据 1:1 重现那个瞬间来定位原因。如果你的系统充满随机性和不确定调度，你就永远无法在实验室里重现现场——那 bug 就成了永远抓不住的幽灵。可复现性是自动驾驶工程的地基，这也是为什么 9.1 那个手写仿真器我坚持用固定步长。

小结

  • 自动驾驶的测试金字塔底座是单元测试，中间厚厚两层是本行业特色的录制回放回归与闭环仿真场景测试，顶端是昂贵的真车测试。
  • Rust 把测试做成语言一等公民：#[cfg(test)] 内联单元测试、tests/ 目录集成测试，cargo test 开箱即用；测几何/数值函数时用近似断言，测有状态算法（控制器、滤波器）时测行为契约与不变量，而非魔法数字。
  • proptest 基于属性的测试让机器随机扫雷，最典型的自动驾驶应用是坐标变换往返等价和控制器/角度不变量——它能找到你根本想不到的退化输入。
  • 录制回放测试是自动驾驶测试的王牌：用真实难例数据 + 基线容差做回归，守住"改代码别改坏"这条防线；它是数据闭环的闭合点，也正是你手边 inf/ 评测流水线的使命。
  • 规划/控制用闭环场景测试 + 三类指标（安全红线、舒适、交规与有效性）打分。
  • 区分代码覆盖率与场景覆盖率——后者才是自动驾驶真正爬不完的山。
  • CI 里分层跑测试，快而便宜的在前，贵而慢的在后，快速失败。
  • 确定性与可复现是一切测试的地基：固定随机种子、用逻辑时钟做确定性调度、用容差断言对付浮点；Rust 在编译期消灭数据竞争，替你根除了最恶劣的一类不确定性。

下一节是第九部分的收官，也是最硬核的一节：当代码测得再好，它终究要跑在一块真实的车载芯片上、在实时约束下、承担着安全攸关的责任——我们来谈功能安全（ISO 26262）、SOTIF、实时性，以及 Rust 在其中的优势、陷阱与部署实践。
