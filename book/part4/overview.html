Rust 智能驾驶开发：从小白到工程师

4.1 感知任务总览

从这一章开始，我们进入自动驾驶软件里技术密度最高、最"性感"、也最容易让人陷进去出不来的模块——感知（perception）。前面 1.2、1.3 节我们已经知道：感知的职责是把原始传感器数据，变成一份结构化的世界描述。这一节不写代码，我们先建一张"地图"：感知到底要输出什么、由哪些子任务拼成、走相机还是激光雷达、行业两大路线在争什么、以及你怎么衡量一个感知系统的好坏。

把这一节当成第四部分的目录页。读完你应该能在白板上给面试官画出整个感知栈的框图，并说清每一块的输入输出和难点——这几乎是所有感知岗位面试的开场。

感知到底要输出什么

新手容易以为"感知 = 检测障碍物"。检测确实是核心，但一套量产感知系统的输出远不止于此。把感知的输出摊开，大致是这么几类：

  1. 障碍物（obstacles）：动态和静态的物体——车、人、自行车、锥桶、掉落物。每个障碍物带位置、大小、朝向、速度、类别、跟踪 ID、以及置信度。这就是我们在 1.3 节定义的 Obstacle 结构。它是感知最重要的输出，因为下游的预测和规划几乎全靠它。
  2. 车道线与道路结构（lane lines / road structure）：当前车道、相邻车道、车道线类型（实线/虚线）、路沿、停止线。它告诉规划"路在哪、能不能变道"。
  3. 可行驶区域（drivable area / freespace）：一张"哪里能开、哪里不能开"的栅格或多边形。它和障碍物是互补的——障碍物是"这里有个东西"，可行驶区域是"这一整片是空的"。对付长尾障碍物（没见过的奇怪物体）时，freespace 常常是最后的安全网。
  4. 交通信号（traffic light / sign）：红绿灯的位置和状态（红/黄/绿/箭头）、限速牌、禁行标志。注意：红绿灯与哪条车道关联这件事，往往要结合高精地图才能确定，纯感知给不了。
  5. 语义信息（semantics）：更细粒度的场景理解——这是人行横道、那是减速带、前方在施工。越往端到端走，这类"软"语义越重要。

中高级视角：初级工程师盯着"障碍物检测的 mAP 又涨了 0.5"，高级工程师问的是"我们的 freespace 在雨夜对黑色障碍物的召回率是多少、掉了会不会撞上去"。感知的价值不在于某个指标的小数点，而在于整个输出集合能不能撑住下游对安全的要求。

四个动词：检测、分割、跟踪、融合

感知内部由四类基本任务反复组合而成。理解它们的关系，比记住任何一个网络名字都重要。

  • 检测（detection）：在图像或点云里找出物体，给出它的框（2D 框或 3D 框）和类别。回答"哪里有什么"。
  • 分割（segmentation）：给每个像素（或每个点）打一个类别标签。语义分割（semantic）只分类别；实例分割（instance）还区分"这是第 1 辆车、那是第 2 辆车"。可行驶区域通常就是分割出来的。
  • 跟踪（tracking）：把跨帧的同一个物体关联起来，给它一个稳定的 ID，并顺带估计它的速度。检测是"这一帧看到什么"，跟踪是"这一帧的车 A 就是上一帧的车 A"。4.5 节整章讲它。
  • 融合（fusion）：把多个传感器（相机 + 激光雷达 + 毫米波）或多个时刻的信息合并成一个统一、更可信的世界模型。融合也在 4.5 节详述。

它们的典型串联是这样一条链：

   原始数据
      │
      ▼
  ┌────────┐   ┌────────┐
  │  检测   │   │  分割   │     （逐帧、单传感器）
  └────────┘   └────────┘
      │            │
      └─────┬──────┘
            ▼
        ┌────────┐
        │  融合   │            （跨传感器：相机+激光+雷达）
        └────────┘
            ▼
        ┌────────┐
        │  跟踪   │            （跨时间：给 ID、估速度、平滑）
        └────────┘
            ▼
     结构化世界模型  →  Vec<Obstacle> + 车道 + freespace + 红绿灯

注意这条链在不同公司顺序会变：有的先在各传感器上分别检测+跟踪，再做目标级融合（后融合）；有的把原始数据先融合成统一表示，再一次性检测（前融合）。这正是 4.5 节要展开的"前融合 vs 后融合"之争。

2D 感知 vs 3D 感知

这是新人最容易混淆、面试官最爱追问的一对概念。

  • 2D 感知：在图像平面上工作。输出是像素坐标下的 2D 框、2D 分割。优点是数据密集、纹理丰富、网络成熟（YOLO、Mask R-CNN 那一票）。致命缺点：图像丢了深度。一个 2D 框告诉你"图像里第 800 行第 1200 列有辆车"，但那辆车离你 10 米还是 50 米？规划要的是米，不是像素。
  • 3D 感知：直接在三维物理空间里工作，输出带真实尺寸和位置的 3D 框（x, y, z, 长宽高, 朝向）。这正是 Obstacle.position / Obstacle.size 需要的东西。3D 检测可以来自激光雷达点云，也可以来自单目/多目图像（"单目 3D 检测"，靠先验估深度，误差大）。

关键认知：规划和控制活在 3D 物理世界里，所以感知最终必须输出 3D。2D 感知要么用来辅助（比如在图像上先检测再投影到 3D），要么靠标定关系和地面假设把 2D 框"抬"到 3D（会引入深度误差）。这就是为什么纯视觉方案在测距上天生更吃力——后面讲路线之争会再谈。

面试题：给你一个图像上的 2D 车辆框，怎么估算它在自车坐标系下的距离？ 答：最朴素的办法是地平面假设——假设框的底边压在地面上，已知相机的内参和外参（安装高度、俯仰角），把底边中点这条视线与"地面平面（z=0）"求交点，得到 3D 位置。这套几何我们在 4.2 节讲坐标映射时会用到。它的问题是：一旦地面不平、或框底没压在地上（比如被遮挡），距离就飘了。这也是纯视觉测距的经典软肋。

三条技术路线：相机、激光雷达、融合

选传感器就是选路线。三种主传感器的取舍，你必须背下来（3.1 节讲过硬件，这里从感知视角复盘）：

维度相机（camera）激光雷达（LiDAR）毫米波雷达（radar）
本质数据稠密 2D 像素、有颜色纹理稀疏 3D 点云、有精确距离稀疏目标、有径向速度
测距精度差（要估）很好（厘米级）好（径向）
直接测速不能（要跨帧算）不能（要跨帧算）能（多普勒）
分类能力强（红绿灯、字、颜色全靠它）中（靠形状）弱
恶劣天气差（雨雾夜）中（雨雪有噪点）强（几乎不受影响）
成本低高（在降）低
分辨率高中低

看这张表你会立刻明白两件事：

  1. 没有一种传感器是全能的。相机看得懂"是什么"但不知道"多远"；激光雷达知道"多远、什么形状"但不认识红绿灯的颜色；雷达在雨雾里还能直接给你速度，但分辨率低到分不清是人还是电线杆。
  2. 它们的优缺点高度互补。这正是"多传感器融合"的物理动机——用雷达的全天候测速、补激光雷达的精确几何、加相机的语义分类，拼出一个比任何单传感器都强的世界模型。

纯视觉 vs 多传感器：一场还在打的仗

行业里有一场著名的路线之争，面试常聊，你要能中立地说清双方的逻辑。

纯视觉派（以特斯拉为代表）：只用相机（+ 少量雷达甚至去掉雷达）。逻辑是——人类就是靠两只眼睛开车的，视觉信息熵最高，只要神经网络足够强、数据足够多，深度和速度都能从视频里学出来（"占用网络 occupancy network"就是让网络直接预测 3D 空间的占用）。优势：成本低、易量产、纯视觉数据规模能滚起飞轮。软肋：测距/测速依赖模型估计，corner case（强光、逆光、纯色大卡车横在路上）下深度会崩，缺少物理冗余。

多传感器派（以 Waymo 为代表）：相机 + 激光雷达 + 雷达全上。逻辑是——安全攸关的系统必须有物理级冗余，激光雷达给的是测量的深度而不是估计的深度，宁可贵也不赌模型。优势：几何精度高、冗余强、long tail 更稳。软肋：成本高、传感器标定与同步复杂、激光雷达在极端天气也有噪点。

真实项目里：这场争论没有"正确答案"，它是成本、安全等级、量产规模、目标 ODD（运行设计域）四者的权衡。Robotaxi（要在无人监管下运营）几乎都上激光雷达；量产辅助驾驶（有人类兜底）更倾向压成本走视觉重、雷达/激光轻的路线。作为工程师，你要会的是两套技术栈都能上手——本书 4.2/4.3 讲视觉与推理，4.4 讲点云，4.5 讲怎么把它们融合起来。

你怎么知道感知做得好不好：评价指标

没有指标就没有工程。感知的核心指标你必须理解其定义，而不是只会念缩写。

IoU（Intersection over Union，交并比）：衡量预测框和真值框重合程度。

$$ \text{IoU} = \frac{|A \cap B|}{|A \cup B|} $$

即"两个框交集面积 / 并集面积"。IoU=1 是完美重合，IoU=0 是完全不沾边。通常约定 IoU ≥ 0.5（或 0.7）才算"检测对了"。它是几乎所有检测/分割指标的基石。

Precision 与 Recall（精确率与召回率）：

  • 精确率 = 预测出的框里，有多少是真的对的（TP / (TP + FP)）。低精确率 = 满屏幻觉框（误检）。
  • 召回率 = 所有真实物体里，有多少被检出来了（TP / (TP + FN)）。低召回率 = 漏检——在智驾里漏检比误检致命得多，漏掉一个横穿的行人就是事故。

mAP（mean Average Precision，平均精度均值）：目标检测最常用的综合指标。对每个类别，扫过不同置信度阈值画出 Precision-Recall 曲线，曲线下面积就是该类的 AP；对所有类别求平均得到 mAP。它同时惩罚误检和漏检，是检测模型的"总分"。KITTI、nuScenes 这些数据集的排行榜比的就是它。

MOTA（Multiple Object Tracking Accuracy，多目标跟踪准确度）：衡量跟踪好坏，把三种错误算进去：

$$ \text{MOTA} = 1 - \frac{\sum_t (\text{FN}_t + \text{FP}_t + \text{IDSW}_t)}{\sum_t \text{GT}_t} $$

其中 FN 是漏跟、FP 是错跟、**IDSW（ID Switch，ID 跳变）**是"同一个物体的 ID 中途换了"——这是跟踪特有的病，规划最怕它，因为 ID 一跳，速度估计和意图历史全乱。MOTA 越接近 1 越好（甚至可能为负，说明错误比目标还多）。4.5 节我们会实打实地和 IDSW 搏斗。

面试题：为什么感知常常宁可要"稍微多一点误检"，也不要"漏检"？ 答：因为代价不对称。误检（幻觉出一个不存在的障碍物）最坏的结果是急刹或绕行，体验差但安全；漏检（真障碍物没看到）可能直接导致碰撞。所以感知的工作点往往偏向高召回，把"筛掉误检"的一部分压力交给下游的跟踪、融合和规划的时序确认。但也不能无脑高召回——满屏幻觉会让车"幽灵刹车"，同样危险。这个平衡点，就是感知工程师的手艺。

感知系统的"三条时间线"：单帧、时序、多传感器

上面的框图容易让人误以为感知是"一帧进、一帧出"的纯函数。真实的感知系统同时活在三条时间线上，理解这个才算入门：

  1. 单帧（single-frame）：这一瞬间，每个传感器各自看到了什么。检测和分割主要在这条线上工作——输入一帧图像/点云，输出这一帧的框和分割。它是无记忆的。
  2. 时序（temporal）：把连续多帧串起来。跟踪活在这条线上——它记得"上一帧那辆车在哪、多快"，用来给这一帧的目标续上 ID 和速度。感知一旦上了时序，就从"拍照片"变成了"看视频"，能抗单帧的抖动、遮挡、漏检。
  3. 多传感器（multi-sensor）：同一瞬间，不同传感器（相机、激光、雷达）从不同物理原理看同一个世界。融合活在这条线上——把多个视角缝成一个。

这三条线交织出感知的真正复杂度。举个具体的例子：一个行人这一帧被前车短暂遮挡（单帧检测漏了），但跟踪（时序线）靠运动模型知道"他应该还在那，只是被挡住了"，同时雷达（多传感器线）虽然看不清形状却依然测到那个位置有个带速度的回波——三条线合起来，系统才没有让这个行人"凭空消失"。任何一条线单独都会出错，合起来才鲁棒。 这也解释了为什么感知代码远不止"调用一个检测网络"那么简单。

坐标系：感知输出到底"在哪个系里"

一个绕不开、且新手必栽的问题：感知输出的位置，是在哪个坐标系下的？（3.2 节讲刚体变换，这里先建立感知视角的意识。）

  • 传感器坐标系：检测网络直接输出的，往往是各传感器自己的坐标——图像像素坐标、激光雷达自己的坐标原点。
  • 自车坐标系（ego frame）：以车辆某个基准点（常是后轴中心）为原点。1.3 节的 Obstacle.position 就是在这个系下——"前方 30 米、右侧 1.5 米"。感知的标准输出坐标系通常是它，因为规划/控制都在自车系里思考。
  • 地图坐标系（map/world frame）：全局的、固定的坐标。要把障碍物放进地图（判断它在哪条车道、离红绿灯多远），得靠定位（第五部分）把自车系换算到地图系。

所以感知内部至少要做一次坐标变换：把各传感器坐标下的检测，统一到自车坐标系再输出。这一步用到传感器的外参（extrinsics）——传感器相对车体的安装位置和角度，靠**标定（calibration）**得到。外参标定差一点，障碍物位置就系统性偏移，融合时不同传感器还会"对不齐"。

面试题：感知模块应该输出自车坐标系还是地图坐标系下的障碍物？ 答：一般输出自车坐标系。原因有二：① 感知不该依赖定位——万一定位挂了（隧道里 GPS 失效），感知在自车系里照样能工作、照样能刹车，这是安全解耦。② 下游对不同坐标系各取所需：控制只关心"障碍物相对我在哪"（自车系天然够用），预测/规划要放进地图上下文时，再由它们用定位结果做变换。把坐标变换的依赖往后推，是模块解耦的好设计。

感知最难的地方：长尾、遮挡、恶劣天气

如果感知只需要在晴天的高速上认车，这领域早就解决了。它难，难在分布的尾巴。你必须理解三类经典难题，它们是感知工程师真正的战场：

  • 长尾（long tail）：99% 的场景是常见的（车、人、自行车），但剩下 1% 是无穷无尽的怪东西——横在路上的白色大卡车、掉落的轮胎、路上的沙发、奇装异服的行人、举着广告牌的人。检测网络没见过的就可能漏检，而漏检在智驾里是致命的。应对：一半靠数据闭环不断挖掘难例喂训练（inf/ 那类离线推理/评测流水线就服务于此），一半靠不依赖类别的几何方法（4.4 的点云聚类、freespace）兜底——"我不知道那是啥，但那里有一坨东西，别撞上去"。
  • 遮挡（occlusion）：目标被部分或完全挡住。部分遮挡让检测框和特征残缺，完全遮挡让目标"消失"。应对：靠时序跟踪维持被遮挡目标的存在（4.5），靠多传感器从不同角度补看。
  • 恶劣天气与光照（adverse conditions）：雨、雪、雾、逆光、夜间、隧道进出口的明暗突变。相机在这些条件下急剧退化，激光雷达在雨雪里出噪点。应对：靠传感器冗余（雷达几乎不受天气影响）、靠针对性的数据增强和训练。

真实项目里：一个感知系统在 demo 视频里 99% 的准确率毫无意义——决定它能不能上路的，是那最后 1% 的长尾。行业里流传一句话："自动驾驶的最后 10% 要花 90% 的力气。" 这 10% 几乎全是长尾和 corner case。所以现代感知的竞争，本质是数据闭环效率的竞争——谁能更快地发现难例、标注、训练、验证、上车。这也是 1.2 节把"数据闭环"列为三根支柱之一、以及本书反复提到 inf/ 这类离线推理基础设施的原因。

感知与下游的契约：别越界，也别漏项

最后强调感知的接口契约，这是模块化架构（1.2 节）的精髓。感知该做什么、不该做什么，边界要清晰：

  • 感知做：把传感器数据变成"此刻世界有什么"——障碍物（带位置/速度/类别/ID/不确定性）、车道线、freespace、红绿灯状态、语义。
  • 感知不做："他接下来要干什么"（那是预测）、"我该怎么走"（那是规划）。感知只报告观测到的现在，不做意图推断和决策。

这个边界为什么重要？因为混淆职责会让系统无法测试和调试。如果感知偷偷做了点预测（比如"我觉得这人要横穿所以提前报警"），当系统出问题时你就分不清是感知看错了还是预测判断错了。清晰的契约让每个模块可以独立验证——感知的指标（mAP/MOTA）只衡量"看得准不准"，不掺杂下游逻辑。这是 1.3 节那句"感知只负责看到，不负责预判"的工程价值所在。

实时性与算力预算：感知的隐形天花板

上面聊的都是"看得准不准"，但感知还有一条同样致命的约束：看得够不够快。1.2 节讲过端到端时延是安全的生命线，感知往往是这条链路里最吃算力、最耗时的一环。

算一笔账。假设感知要跑 10 Hz（每 100 毫秒一帧），而这 100 毫秒里塞着：多路相机的图像检测、点云的 3D 检测、分割、跟踪、融合……每个神经网络前向就要几毫秒到几十毫秒，多路一叠加，预算瞬间见底。而车载计算平台（如 NVIDIA Orin）的算力是固定且昂贵的，功耗、散热、成本都有硬上限——你不能像云端那样想加卡就加卡。

这带来一连串工程权衡，全是感知工程师的日常：

  • 模型选择：用精度高但慢的大模型，还是精度稍低但快的小模型？（4.4 提的 PointPillars 之所以流行，就是因为它够快。）
  • 分辨率与降采样：图像要不要降分辨率？点云要不要下采样（4.4 的 voxel）？降了省算力但可能漏掉远处小目标。
  • 量化与加速：int8 量化、TensorRT（4.3 节）——用少量精度换数倍速度，边缘部署几乎必用。
  • 调度：哪些任务必须每帧跑，哪些可以隔帧跑（比如红绿灯检测不必 30 Hz）？多个模型怎么在 GPU 上流水线并行、错峰调度？

中高级视角：初级工程师的世界里只有 mAP，高级工程师的世界里是 mAP / 延迟 / 算力 / 功耗的四维帕累托前沿。"把 mAP 提高 1 个点但推理慢一倍"在论文里是进步，在车上很可能是倒退——因为多出来的延迟直接吃掉安全裕度。真实的感知优化，一大半是在这个约束曲面上找平衡点，而不是无脑追精度。这也是为什么 Rust 在感知部署（而非训练）里越来越有价值——它能在不牺牲安全的前提下榨出性能，没有 GC 停顿这种实时系统杀手。

一个正在发生的变化：端到端与占用网络

1.2 节提过模块化 vs 端到端之争，在感知里这场争论有个具体的落点，你该知道：

传统模块化感知的输出是离散的障碍物列表——一个个框。但框有个根本缺陷：它假设世界能被切成一个个"物体"。可现实里很多东西不好框——一片灌木丛、一堆散落的货物、道路施工的复杂区域、半个探出来的车头。硬要用框描述，要么框不准，要么直接漏掉。

占用网络（occupancy network）是新思路，特斯拉带火的。它不输出框，而是把车周围的 3D 空间切成一个个小格子（voxel），直接预测每个格子是被占用还是空的（以及占用物的语义、甚至运动）。这本质是一种稠密的、不依赖"物体"概念的表示——它天然能描述任何形状的障碍物，包括长尾的怪东西，因为它只回答"这个格子里有没有东西挡路"，而不需要先认出"这是什么物体"。

这和 4.4 节要讲的 BEV（鸟瞰图）表示、以及"不依赖类别的几何/freespace 方法"是同一股潮流的不同侧面：从"检测物体"转向"理解空间占用"。它的优势是对长尾天然友好、和规划要的表示更接近；代价是算力大、训练数据要求高、可解释性差。

作为读者，你现在只需记住：框不是唯一的世界表示，稠密占用/BEV 是感知的重要演进方向，本书 4.4 会讲 BEV 的构造，让你对这股潮流有动手层面的理解。

有了上面的词汇，第四部分剩下四章这样铺开：

  • 4.2 图像处理基础与 Rust 实现：像素、颜色空间、张量、推理前处理。喂给神经网络之前，图像要怎么被 Rust 摆弄成 NCHW 张量。这是所有视觉感知的地基。

  • 4.4 点云处理与激光雷达感知：点云数据结构、体素下采样、RANSAC 地面分割、kd-tree 加速的欧式聚类、PointPillars/CenterPoint 与 BEV。有数学、有算法、有可跑代码。

小结

  • 感知的输出是一整套结构化世界描述：障碍物、车道线、可行驶区域、红绿灯、语义——不是只有障碍物检测。
  • 四个基本动词——检测、分割、跟踪、融合——反复组合成整条感知链；顺序（先融合还是先跟踪）就是前/后融合之争。
  • 2D 感知丢了深度，规划要的是 3D；感知最终必须输出 3D，这是纯视觉测距天生吃力的根源。
  • 相机、激光雷达、雷达三者高度互补，没有全能传感器；纯视觉（特斯拉）与多传感器（Waymo）之争本质是成本、安全、量产、ODD 的权衡。
  • 指标要懂定义：IoU 是基石，mAP 是检测总分，MOTA/IDSW 是跟踪的命门；智驾里漏检比误检致命，工作点偏高召回。
