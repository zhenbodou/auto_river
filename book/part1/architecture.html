Rust 智能驾驶开发：从小白到工程师

1.2 一辆自动驾驶车的软件全景

上一节我们从"责任"的角度理解了分级。这一节我们打开引擎盖，看软件。看完你应该能在白板上画出一整套系统——这是很多中高级面试的开场题。

从"数据"的视角看整台车

不要把自动驾驶想成"一个很聪明的 AI 在开车"。把它想成一条数据流水线：传感器每秒产生海量原始数据，经过层层加工，最后变成方向盘转角和油门刹车的电信号。

       物理世界
          │  (光子、回波、卫星信号、车轮转动)
          ▼
   ┌─────────────┐
   │   传感器层    │  相机/激光雷达/毫米波/IMU/GNSS/轮速
   └─────────────┘
          │  原始数据 (图像帧、点云、IMU 读数...)
          ▼
   ┌─────────────┐   ┌──────────────┐
   │    感知      │   │   定位/建图   │   "我周围有什么" + "我在哪"
   └─────────────┘   └──────────────┘
          │                 │
          └────────┬────────┘
                   ▼
            ┌─────────────┐
            │    预测      │   "他们接下来要干什么"
            └─────────────┘
                   ▼
            ┌─────────────┐
            │    规划      │   "所以我该怎么走"
            └─────────────┘
                   ▼
            ┌─────────────┐
            │    控制      │   "方向盘转 3.2°，油门 15%"
            └─────────────┘
                   ▼
            ┌─────────────┐
            │  线控执行器   │   转向电机、刹车、油门
            └─────────────┘
                   ▼
              车辆运动 ──→ (改变物理世界，形成闭环)

这条链路每秒要跑很多遍（通常 10–100 Hz），而且每一环的延迟都会累加。从一个行人出现在相机里，到车真的开始刹车，整个链路的端到端时延（end-to-end latency）是安全的生命线。中高级工程师脑子里必须随时有这根"时延预算"的弦。

五大功能模块

后续各部分会逐个深入，这里先给每个模块一句话定位和它的输入/输出：

感知 (Perception)

  • 一句话：把原始传感器数据变成"结构化的世界描述"。
  • 输入：图像、点云、雷达回波。
  • 输出：一份障碍物列表——每个障碍物有位置、大小、朝向、速度、类别（车/人/自行车）、以及跟踪 ID；还有车道线、可行驶区域、红绿灯状态等。
  • 难点：遮挡、恶劣天气、长尾场景（没见过的奇怪物体）。

定位 (Localization)

  • 一句话：厘米级地知道"我在地图上的哪个位置、朝哪个方向"。
  • 输入：GNSS、IMU、轮速、以及感知到的地图特征（车道线、路牌）。
  • 输出：车辆的 6 自由度位姿（位置 x/y/z + 姿态 roll/pitch/yaw），通常在高精地图坐标系里。
  • 难点：隧道/城市峡谷里 GPS 失效、长时间无特征路段的漂移。

预测 (Prediction)

  • 一句话：预判周围每个交通参与者未来几秒的轨迹。
  • 输入：感知输出的障碍物列表（带历史轨迹）+ 高精地图。
  • 输出：每个目标的多条可能未来轨迹及其概率。
  • 难点：人的意图不可观测，只能从行为推断；博弈（他会不会让我）。

规划 (Planning)

  • 一句话：在满足安全、舒适、交规、效率的前提下，算出自车未来几秒要走的一条轨迹。
  • 输入：自车位姿、障碍物预测、地图、导航目标。
  • 输出：一条时空轨迹（一串带时间戳的位置+速度点）。
  • 难点：多约束下的实时优化、和其他车的博弈、罕见场景的兜底。

控制 (Control)

  • 一句话：让车精确地跟上规划给出的轨迹。
  • 输入：规划轨迹 + 当前车辆状态。
  • 输出：方向盘转角、油门开度、刹车力（发给线控底盘）。
  • 难点：车辆动力学的非线性、执行器延迟、不同路面/载重下的适应。

支撑这一切的三根柱子

光有五大模块还跑不起来。真实系统还需要：

  1. 中间件 (Middleware)：模块通常是独立的进程甚至独立的计算单元，它们之间要高效、可靠地传消息。这就是 ROS 2、DDS、Zenoh 干的事（第八部分）。这里 Rust 大有可为。
  2. 地图 (Map)：高精地图（HD Map）给定位、预测、规划提供"先验知识"——车道拓扑、限速、红绿灯位置。
  3. 数据闭环 (Data Loop)：车队采集数据 → 挖掘难例 → 标注 → 训练模型 → 仿真验证 → 部署上车。现代自动驾驶的竞争力，很大程度上是这套闭环的效率之争。

本书关联：你工作环境里那个 inf/ 目录（一套视频/算法推理 SDK 的 Rust 移植）就属于"数据闭环"里的推理/评测环节——把采集的视频喂给模型、跑推理、产出结构化结果供评测。这类"离线大规模推理流水线"是数据闭环的关键基础设施，也是 Rust 在智驾里已经落地的真实场景之一。

两种架构范式：模块化 vs. 端到端

你必须知道行业正在发生的一场路线之争：

  • 模块化 (Modular)：就是上面画的那条流水线，每个模块单独开发、单独测试、接口清晰。可解释、可调试、可局部升级，是目前绝大多数量产系统的架构。
  • 端到端 (End-to-End)：用一个（或少数几个）大神经网络，直接从传感器输入映射到规划/控制输出，中间不再有人为定义的"障碍物列表"这种接口。特斯拉 FSD v12+、以及大量最新研究在往这个方向走。上限高、能处理长尾，但难解释、难调试、对数据量要求极高。

现实是混合的：即使宣称端到端的系统，通常也保留了模块化的安全兜底层。对你的意义是：模块化的知识仍然是根基——它定义了这个领域的词汇和评价标准，即使未来更端到端，你也需要用这些概念去理解和验证系统。本书以模块化为主线，并在感知（第四部分）和规划（第六部分）里介绍端到端的思路。

小结

  • 把自动驾驶理解成一条实时数据流水线：传感器 → 感知/定位 → 预测 → 规划 → 控制 → 执行器 → 闭环。
  • 五大模块各有明确的输入/输出契约，请把这张表记牢——它是你和同事、和面试官的通用语言。
  • 端到端时延贯穿始终，是安全的生命线。
  • 中间件、地图、数据闭环是让系统真正跑起来的三根支撑柱，Rust 在中间件和数据闭环里已经落地。
  • 模块化 vs. 端到端是当下的路线之争，但模块化知识是不可绕过的根基。
