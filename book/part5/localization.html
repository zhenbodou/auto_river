5.2 定位：GNSS/IMU 组合导航与地图匹配

上一节我们把卡尔曼滤波这台"融合机器"造好了。这一节把它开上路——回答自动驾驶里那个看似简单、实则要人命的问题：车此刻在世界的哪个位置、朝哪个方向？

你可能觉得"不就是 GPS 吗，手机都能定位"。但手机导航把你定位到"这条路上"就够了，误差十几米无所谓；自动驾驶要知道自己在哪条车道的哪个位置，误差得压到厘米到分米级，还得在 GPS 完全失效的隧道里连续几十秒不飘。这中间的鸿沟，就是这一章的内容。定位做不好，后面的预测、规划、控制全建在流沙上——它是整个自动驾驶栈里最"低调但致命"的模块。

一、定位问题的严格定义

定位（localization）要输出的，是自车在某个地图坐标系（map frame） 下的 6 自由度位姿（6-DoF pose）：3 个平移（位置 $x,y,z$）+ 3 个旋转（航向 yaw、俯仰 pitch、横滚 roll）。我们复用第 1.3 节定义的 Pose：

#![allow(unused)]
fn main() {
#[derive(Debug, Clone, Copy)]
pub struct Pose {
    pub position: [f64; 3],   // 在“地图坐标系”下的位置 (米)
    pub yaw: f64,             // 航向角 (弧度)
    pub pitch: f64,
    pub roll: f64,
}
}

但一个上路的定位系统，光给位姿是不够的，它必须同时给出这个位姿有多可信——也就是协方差。所以工程上真正的定位输出更像这样：

/// 带不确定性的定位结果。规划/控制需要根据协方差决定“敢开多快、敢贴多近”
#[derive(Debug, Clone)]
pub struct LocalizationResult {
    pub pose: Pose,
    pub velocity: [f64; 3],       // 地图系下的速度
    pub covariance: [[f64; 6]; 6],// 6-DoF 位姿协方差（回忆 5.1 的 P）
    pub status: LocalizationStatus,
    pub timestamp: f64,
}

#[derive(Debug, Clone, Copy, PartialEq)]
pub enum LocalizationStatus {
    Aligning,     // 初始化对齐中，结果不可用
    Good,         // 多源可用，高精度
    Degraded,     // 部分源失效，靠推算维持，精度下降
    Lost,         // 已发散，下游必须降级处理
}

注意 status 字段——定位系统必须诚实地告诉下游"我现在行不行"。一个假装自己还很准、实则已经在隧道里飘了 20 米的定位模块，比一个老实说"我 Degraded 了"的危险得多。这个诚实性，是安全设计的一部分。

关于地图坐标系：因为地球是曲面，全局用经纬度不方便做平面几何，实践中通常把局部区域投影到平面直角坐标系——常用 UTM（Universal Transverse Mercator） 投影，或者以某个原点建立的局部东北天（ENU: East-North-Up） 坐标系。定位和高精地图共用这一套坐标，规划才能在同一个平面上算几何。坐标系与刚体变换的细节见第 3.2 节，这里只需记住：定位的输出、高精地图、感知结果最终都要被搬到同一个坐标系里对齐，这是万物的前提。

二、GNSS/RTK：能给你绝对位置，但不总在

GNSS（Global Navigation Satellite System，全球卫星导航系统） 是 GPS、北斗、GLONASS、Galileo 的统称。原理是三边测量：接收机测出自己到 4 颗以上卫星的距离（靠信号飞行时间），解一个方程组得到 3D 位置 + 钟差。为什么要 4 颗而不是 3 颗？因为接收机的时钟和卫星原子钟不同步，多出一个未知的钟差，需要第 4 个方程来解。

裸 GNSS 的精度只有米级，远不够用。要到厘米级，靠 RTK（Real-Time Kinematic，实时动态差分）：在已知精确坐标的地面基站上放一台接收机，它测出"卫星信号误差"（电离层延迟、对流层延迟、卫星轨道误差这些对邻近区域几乎相同的系统误差），实时播发给车上的流动站做差分改正。RTK 好的时候能到 1~2 厘米，是量产定位的重要一环。

但 GNSS 的局限，恰恰在自动驾驶最需要的地方暴露：

  • 城市峡谷（urban canyon）：高楼把卫星信号挡住或反射。多路径（multipath） 是头号杀手——信号撞墙再进天线，飞行时间变长，位置能瞬间跳偏几十米，而且接收机常常不知道自己错了（还报着高置信度）。这是定位里最阴险的野值来源。
  • 隧道、地库、高架桥下：直接没信号。GNSS 输出中断，一秒都没有。
  • RTK 的额外脆弱：依赖基站数据链（4G/专网）不断线，依赖"整周模糊度固定"（fix）状态——一旦失锁重新收敛要数秒，这几秒里精度掉到分米甚至米级。
  • 更新率低：典型 GNSS 只有 1~10 Hz，而车 100 km/h 时 10 Hz 意味着两帧之间已经开出去近 3 米。控制环需要更高频、更平滑的位姿。

结论很清楚：GNSS 给你宝贵的"绝对位置锚点"，但它低频、间歇、偶尔骗你。你不能直接用它开车，必须把它和别的东西融合。 那个"别的东西"，第一个就是 IMU。

三、IMU 航位推算：高频平滑，但会漂

IMU（Inertial Measurement Unit，惯性测量单元） 提供高频（100~1000 Hz）的 3 轴加速度和 3 轴角速度。它的美妙之处是完全自包含——不依赖任何外部信号，隧道里、地库里照样工作。

航位推算（dead reckoning） 就是纯靠 IMU 递推位姿：把角速度积分得到姿态，把加速度（先用姿态转到地图系、扣掉重力）积分一次得速度、再积分一次得位置。听起来完美，直到你意识到那个致命词：积分。

IMU 每个读数都有小小的偏置（bias）和噪声。加速度积分两次才到位置，误差被双重积分放大——bias 里一个恒定的小偏差，积分两次会变成随时间平方增长的位置误差。这叫漂移（drift）。一个消费级 IMU 纯推算几秒钟就能飘出几米；哪怕是昂贵的战术级 IMU，纯惯性也撑不了太久。

所以 IMU 单独用不了，但它和 GNSS 是天生一对：

维度GNSS/RTKIMU
误差特性无偏但有噪声、会跳变短期极平滑、长期漂移
频率低（1~10 Hz）高（100~1000 Hz）
可用性露天好，遮挡处失效永远可用
绝对/相对绝对位置相对增量

一个管"长期不跑偏"、一个管"短期平滑高频"，完美互补。把它们融合的技术，就叫组合导航（integrated navigation），而融合的引擎，正是上一章的（扩展）卡尔曼滤波。

四、GNSS/IMU 组合导航：把 5.1 接到车上

组合导航的思路，直接就是 5.1 里那个 GPS+IMU 玩具例子的工业升级版：

  • IMU 驱动预测步（高频）：每来一帧 IMU（比如 200 Hz），用它的角速度、加速度做一次状态预测。这一步让位姿以 IMU 的高频率平滑更新，$P$ 逐渐增大。
  • GNSS 驱动更新步（低频）：每来一帧 GNSS（比如 5 Hz），把它当测量做一次更新，把估计拉回绝对位置，$P$ 被拉小。
  • 因为姿态、重力方向都非线性，实际用的是 EKF（回忆 5.1 第六节）。

一个能长期稳定的组合导航，状态里不只有位姿速度，还要把 IMU 的偏置也当成状态估进去——这是量产系统和教科书例子的关键差别。因为 bias 会缓慢漂移，你得让滤波器实时估计它并扣除，否则漂移照旧。典型 15 维状态（这就是业界常说的 ESKF / error-state 组合导航的规模）：

$$ x = [,\underbrace{p_x,p_y,p_z}{\text{位置}},\ \underbrace{v_x,v_y,v_z}{\text{速度}},\ \underbrace{\phi,\theta,\psi}{\text{姿态}},\ \underbrace{b{a,x},b_{a,y},b_{a,z}}{\text{加速度计偏置}},\ \underbrace{b{g,x},b_{g,y},b_{g,z}}_{\text{陀螺偏置}},] $$

在写代码前，先厘清一个每个组合导航工程师都要能张口就答的概念——松耦合与紧耦合（loose vs tight coupling）：

  • 松耦合（loosely coupled）：GNSS 接收机先自己解算出"位置/速度"这个成品，再作为测量喂进 EKF。简单、模块解耦，是入门和很多量产系统的选择。缺点是当可见卫星少于 4 颗（城市峡谷常见）时，接收机根本给不出解，这一路就整个哑了。
  • 紧耦合（tightly coupled）：不等接收机出成品，直接把原始伪距、多普勒（每颗卫星的测量）喂进 EKF。哪怕只看得到 2~3 颗星，这些"半成品"仍能约束状态。城市峡谷里紧耦合明显更稳，代价是实现复杂、要处理卫星钟差/星历等一堆底层细节。
  • 还有深耦合（deeply/ultra-tightly coupled），把融合结果反馈去辅助接收机的信号跟踪环路，主要见于军用/高动态场景，量产少见。

本节代码演示的是松耦合（GNSS 出 $[x,y]$ 位置成品再融合），因为它最能凸显 5.1 那套预测/更新的骨架。理解了它，紧耦合无非是把观测方程从"位置"换成"到每颗卫星的伪距"（一个非线性 $h$，又要用 EKF 求雅可比了）。

面试题：城市峡谷里为什么紧耦合比松耦合抗得住？ 答：松耦合要求接收机先解出位置，而解位置至少需要 4 颗可见卫星；高楼遮挡下常常不够，松耦合直接无输出。紧耦合用原始伪距，2~3 颗星的测量也能约束滤波器状态，不至于整路失联——它把"够不够解算"的门槛，从接收机层下放到了融合层。

下面是一个组合导航 EKF（松耦合）的 Rust 骨架。为了聚焦融合逻辑，我把状态简化成 2D 平面（位置 2 + 速度 2 + 航向 1 + 陀螺 bias 1 = 6 维），但结构和 15 维完全一致，你能直接看出怎么扩展。用 nalgebra 的动态或定长矩阵均可，这里用定长 SMatrix 表意最清楚。

use nalgebra::{SMatrix, SVector};

const N: usize = 6; // 状态维数: [x, y, vx, vy, yaw, gyro_bias]
type StateVec = SVector<f64, N>;
type StateMat = SMatrix<f64, N, N>;

pub struct IntegratedNav {
    x: StateVec,    // 状态估计
    p: StateMat,    // 协方差 P
    q: StateMat,    // 过程噪声 Q（IMU 噪声 + bias 随机游走）
    last_imu_t: f64,
}

impl IntegratedNav {
    /// 预测步：IMU 到达时调用。accel 为车体系加速度，gyro 为绕 z 的角速度。
    pub fn predict_with_imu(&mut self, accel_body: [f64; 2], gyro_z: f64, t: f64) {
        let dt = t - self.last_imu_t;
        self.last_imu_t = t;
        if dt <= 0.0 || dt > 0.5 { return; } // 时间戳异常保护

        let yaw = self.x[4];
        let bias = self.x[5];
        let omega = gyro_z - bias;                  // 扣除陀螺 bias
        let (s, c) = (yaw.sin(), yaw.cos());

        // 车体系加速度旋到地图系（非线性来源之一）
        let ax_map = c * accel_body[0] - s * accel_body[1];
        let ay_map = s * accel_body[0] + c * accel_body[1];

        // --- 非线性状态预测 x⁻ = f(x, u)（EKF 用原函数推均值）---
        let mut xp = self.x;
        xp[0] += self.x[2] * dt + 0.5 * ax_map * dt * dt; // x
        xp[1] += self.x[3] * dt + 0.5 * ay_map * dt * dt; // y
        xp[2] += ax_map * dt;                             // vx
        xp[3] += ay_map * dt;                             // vy
        xp[4] += omega * dt;                              // yaw
        // xp[5] bias 建模为随机游走，均值不变
        self.x = xp;

        // --- 雅可比 F = ∂f/∂x，代入当前估计点 ---
        let mut f = StateMat::identity();
        f[(0, 2)] = dt;
        f[(1, 3)] = dt;
        // yaw 对位置/速度的偏导（因加速度旋转依赖 yaw）
        f[(2, 4)] = (-s * accel_body[0] - c * accel_body[1]) * dt;
        f[(3, 4)] = ( c * accel_body[0] - s * accel_body[1]) * dt;
        f[(4, 5)] = -dt; // yaw 对 gyro_bias

        // 协方差预测 P⁻ = F P Fᵀ + Q·dt（Q 按时间缩放）
        self.p = f * self.p * f.transpose() + self.q * dt;
    }

    /// 更新步：GNSS 到达时调用，测量 = 平面位置 [x, y]
    pub fn update_with_gnss(&mut self, gnss_xy: [f64; 2], gnss_std: f64) -> bool {
        // 观测矩阵 H：只测位置两维
        let mut h = SMatrix::<f64, 2, N>::zeros();
        h[(0, 0)] = 1.0;
        h[(1, 1)] = 1.0;

        let r = SMatrix::<f64, 2, 2>::identity() * (gnss_std * gnss_std);
        let z = SVector::<f64, 2>::new(gnss_xy[0], gnss_xy[1]);

        let y = z - h * self.x;                       // 新息
        let s = h * self.p * h.transpose() + r;       // 新息协方差
        let s_inv = match s.try_inverse() {
            Some(v) => v,
            None => return false,
        };

        // --- 野值门控：马氏距离超阈值就拒绝这次 GNSS（城市峡谷多路径必备）---
        let nis = (y.transpose() * s_inv * y)[(0, 0)];
        if nis > 9.21 { // 2 自由度卡方 99% 分位
            return false; // 丢弃：很可能是多路径野值
        }

        let k = self.p * h.transpose() * s_inv;       // 卡尔曼增益
        self.x += k * y;

        // Joseph form 保正定（回忆 5.1 第八节）
        let ikh = StateMat::identity() - k * h;
        self.p = ikh * self.p * ikh.transpose() + k * r * k.transpose();
        // 对称化，抹平浮点误差
        self.p = (self.p + self.p.transpose()) * 0.5;
        true
    }

    pub fn pose(&self) -> ([f64; 2], f64) {
        ([self.x[0], self.x[1]], self.x[4])
    }
}

这个骨架已经包含了量产组合导航的四个关键动作：IMU 高频预测、GNSS 低频更新、bias 在线估计、野值门控。把它扩到 3D、加上加速度计 bias 和横滚俯仰，就是一个真正上路的组合导航核心。注意门控那几行——正是它让系统在城市峡谷里能自动识别并丢弃多路径跳变，而不是被带飞。

面试题：为什么组合导航要把 IMU 的 bias 放进状态向量一起估，而不是开机标定好就固定？ 答：因为 bias 会随温度、时间缓慢漂移（bias instability），开机标定的值几分钟后就不准了。放进状态里，滤波器能借助 GNSS 的绝对位置持续观测并修正 bias——这也解释了为什么隧道里待久了精度会掉：没有 GNSS，bias 就没法被继续校正，漂移重新占上风。

五、轮速里程计：便宜好用的第三只手

车轮上的轮速编码器能给出每个轮子的转速，乘以轮子周长就是行驶距离。结合前轮转角（或左右轮差速），可以推算车辆的运动增量——这叫轮速里程计（wheel odometry），本质是另一种航位推算，但特性和 IMU 不同：

  • 优点：几乎免费（车本来就有轮速传感器）、纵向距离测量在正常行驶时相当准、低速和静止时比 IMU 可靠（IMU 静止时积分噪声反而突出）。
  • 缺点：打滑（slip） 时彻底失效——冰雪路面、急加速急刹、原地打方向，轮子转了车没动（或反之），里程计会撒谎。转弯时轮胎侧滑也引入误差。

工程上把轮速也作为一路观测融进 EKF：正常行驶时它给纵向速度一个可靠约束，尤其在 GNSS 失效的隧道里，"IMU + 轮速"的组合比"纯 IMU"漂得慢得多。一个特别有用的技巧是零速修正（ZUPT, Zero-velocity Update）：当轮速和 IMU 都判定车静止时，往滤波器塞一个"速度 = 0"的强测量，能狠狠压住静止时的漂移和 bias。

六、地图匹配定位：让环境本身告诉你在哪

到这里，"GNSS+IMU+轮速"的组合导航已经能给出连续位姿，但在长隧道、卫星长期遮挡时仍会慢慢漂。要真正做到厘米级且不漂，还得让环境特征参与进来——车看到的车道线、路牌、杆状物，本身就藏着位置信息，因为它们在高精地图里有精确坐标。

基于地图特征的匹配

思路：感知模块检测出车道线、交通标志、路灯杆等地图里也标注了的语义特征，把"我观测到的特征位置"和"地图里该特征的位置"对齐，反推自车位姿。

举横向定位一个最实用的例子：车道线。感知说"我右侧 1.6 米有一条车道线"，高精地图说"这条车道线在地图系的 $y=100.0$"。如果我当前估计的位姿让这两者对不上，差值就是一个可以喂进 EKF 的观测——它专门修正横向位置和航向，恰好补上 GNSS 在城市里最弱的那一环。这就是为什么很多量产 L2+ 系统在 GNSS 不佳时仍能稳稳保持车道居中：车道线观测在托底。

#![allow(unused)]
fn main() {
/// 一次车道线横向观测：把“我离车道线多远”与地图对齐，修正横向位姿
pub struct LaneObservation {
    pub lateral_offset: f64,  // 感知测得的自车到该车道线的横向距离 (米)
    pub map_lane_y: f64,      // 地图中该车道线在地图系的横向坐标
    pub std: f64,             // 观测标准差 → R
}
// 观测方程: z = map_lane_y - ego_y  ⇒ 新息 = 观测 offset - 预测 offset
// H 对 y 维为 -1，是一个典型的一维更新，套 5.1 的 update 流程即可。
}

点云配准定位：NDT 与 ICP

更强的一类是激光雷达点云配准定位：预先用采集车把整个区域扫成一张点云地图（point cloud map），车上实时扫到的一帧点云去和这张地图对齐，对齐所需的那个变换，就是车的位姿。两大经典算法（概念层面，第 5.3 会再提）：

  • ICP（Iterative Closest Point，迭代最近点）：反���地"给当前帧每个点找地图里最近的点 → 求最小化总距离的刚体变换 → 应用变换 → 再找最近点"，直到收敛。直观但对初值敏感、最近点搜索开销大。
  • NDT（Normal Distributions Transform，正态分布变换）：把地图空间划成体素网格，每个体素用一个高斯分布描述其中点的分布，然后找一个位姿让当前帧的点落在这些高斯的高概率区域。NDT 对初值不那么敏感、速度快、精度高，是自动驾驶点云定位的主流，Apollo、Autoware 都用它。

点云配准能给出厘米级、且完全不依赖 GNSS 的位姿——这是它在城市和地库封神的原因。代价是：需要预先建好高精点云地图（贵）、需要激光雷达（贵）、地图会因施工/季节变化而过时（需要维护）。它同样作为一路观测融进那个中心 EKF。

中高级视角：注意到没有——车道线、点云配准、GNSS、轮速，全都是往同一个 EKF 里塞观测。这是现代多源融合定位的核心架构：一个中心滤波器维护唯一的位姿状态，各种传感器/算法只负责产出"带协方差的观测"喂进去。这种"松耦合/紧耦合融合"的架构思想，比记住任何单个算法都重要。面试时你能画出"多源观测 → 统一 EKF → 唯一位姿输出 + 故障检测"这张图，档次立刻不一样。

初始对齐：定位的"冷启动"难题

上面 LocalizationStatus 里有个 Aligning 状态，值得单独说——滤波器一上电，它并不知道自己在哪、朝哪。这个"冷启动"问题真实且棘手：

  • 初始位置：靠第一个可用的 GNSS 定点给出，或人工/上次关机位置提供先验。
  • 初始航向（yaw） 最麻烦：静止时 GNSS 给不出航向（没速度就没法从轨迹反推朝向），磁力计又常被车身金属和电磁干扰污染。常见做法是动态对齐——让车往前开一小段，用 GNSS 轨迹方向初始化 yaw；或用双天线 GNSS 直接测航向。
  • 收敛判断：对齐期间 $P$ 很大、status = Aligning，此时定位结果不能给下游用，得等协方差收敛到阈值内才切 Good。

这解释了很多量产车"上电后要等几秒、或缓行一小段才允许开启自动驾驶"的现象——它在等定位对齐收敛。别小看这几秒，冷启动没处理好，车会以一个错误的初始航向一路把估计带偏。

七、工程现实：多源切换与故障检测

真实定位系统 80% 的复杂度，在于没有任何一个源永远可用，你得随时优雅切换。

可用性状态机

不同场景下可信的源不一样，定位系统实质是个状态机：

露天开阔  → GNSS/RTK(fix) + IMU + 轮速          → status: Good（厘米级）
城市峡谷  → 车道线/点云 + IMU + 轮速，GNSS 降权   → status: Good/Degraded
进隧道    → IMU + 轮速 + (若有)点云，GNSS 完全弃用 → status: Degraded（缓慢漂移）
长期失效  → 漂移超阈值                            → status: Lost（触发下游降级/接管）

关键设计：不是非黑即白地"用/不用"某个源，而是动态调它的 $R$（权重）。RTK 失去 fix、只有浮点解时，把它的 $R$ 调大（更不信它）而非直接扔掉；车道线检测置信度低时同理。这种"按可信度连续加权"正是卡尔曼框架的自然表达——回到 5.1 那句话，一切都是按方差加权。

故障检测（fault detection）

  • 新息门控：每一路观测更新前都做马氏距离检验（上面代码里那几行），挡住多路径野值、误检的车道线。这是第一道也是最重要的防线。
  • 多源交叉校验：GNSS 说在 A、点云说在 B，两者差异超阈值 → 至少一个错了，触发告警并降到更保守的模式。
  • 协方差监控：$P$ 的迹（trace）持续增大且不收敛 → 滤波器在发散，置 Lost。
  • 诚实上报：把 LocalizationStatus 和协方差如实传给规划/控制。规划看到 Degraded 就该主动降速、加大安全距离；看到 Lost 就该请求接管或安全停车。定位系统最大的美德是知道自己什么时候不行了——一个自信满满地飘着的定位模块，是自动驾驶事故的经典成因。

真实项目里：定位工程师大量的时间不是在推公式，而是在跑数据、看 bag 回放里哪一帧开始飘、为什么飘。城市峡谷的多路径、过隧道口 GNSS 从有到无那一瞬间的跳变、上下匝道时的俯仰变化、雨雪天车道线检测失效……每一个都是 corner case。本书 inf/ 那套 Rust 离线推理/评测 SDK 的价值就在这里——把海量路测数据离线跑一遍、自动评测定位精度在各场景下的分布，是定位算法迭代的命脉。会写融合算法只是入场券，能建起"数据驱动的评测闭环"才是资深定位工程师的护城河。

小结

  • 定位输出的是地图系下的 6-DoF 位姿 + 协方差 + 状态，其中"诚实上报自己行不行"和位姿本身一样重要。
  • GNSS/RTK 给绝对位置（RTK 可达厘米级），但低频、间歇，在城市峡谷（多路径）和隧道里失效；IMU 高频平滑、永远可用，但双重积分导致快速漂移——两者天生互补。
  • GNSS/IMU 组合导航用 EKF 融合二者，量产系统还把 IMU bias 放进状态在线估计；轮速里程计和零速修正在 GNSS 失效时托底。
  • 地图匹配定位让环境说话：车道线观测修正横向/航向，NDT/ICP 点云配准给出不依赖 GNSS 的厘米级位姿——它们本质都是"往中心 EKF 塞带协方差的观测"。
  • 工程核心是多源动态加权切换 + 故障检测：新息门控挡野值、协方差监控判发散、状态如实上报驱动下游降级。
