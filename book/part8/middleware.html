Rust 智能驾驶开发：从小白到工程师

8.1 自动驾驶中间件全景

第一部分结尾我们埋了一个伏笔：真实的自动驾驶系统不是一个 autonomy_tick() 函数顺序调用，而是一张"并发的、消息驱动的、各跑各频率的节点图"。这一章就来把这句话兑现——用 Rust 真的把这张图搭出来。

而搭图的第一件事，是选一套中间件（middleware）。这一节先建立全景：为什么需要中间件、它提供哪些通信模式、进程内/进程间/跨机各自的代价、以及主流选择（ROS 2、DDS、Zenoh、CyberRT、自研）到底差在哪。读完你应该能在一场技术选型评审会上说清"我们为什么选它"。

为什么需要中间件：先看不用它会怎样

设想你老老实实按第一部分那个函数写：感知、定位、预测、规划、控制全塞进一个进程、一个主循环。会遇到什么？

  • 频率打架。感知跑 10 Hz（等神经网络），控制要 100 Hz（不然车会画龙）。塞在一个循环里，要么控制被感知拖慢，要么你手写一套复杂的分频调度——本质上你在重新发明一个调度器。
  • 一个崩全崩。感知模块一个 panic（或者更现实地，一个第三方 C++ 库段错误），整个进程挂掉，连能安全停车的控制器一起带走。这在车上是不可接受的。
  • 无法独立迭代。感知团队用 CUDA + C++，规划团队想用 Rust，控制团队的代码要过 ISO 26262 认证、动一行都要重新走流程。绑在一个二进制里，谁也别想独立发版。
  • 上不了多机。一台域控制器（domain controller）算力不够，感知要跑在另一块 Orin 上。函数调用可跨不了机器。

所以工业界的答案是：把每个模块做成独立的进程（甚至独立的机器），它们之间用消息通信。 承担"让这些进程高效、可靠地互相发消息"这件事的软件层，就是中间件。

一句话定义：中间件是坐在操作系统之上、应用之下的通信层。它让你写 publish(obstacles) 和 subscribe(obstacles)，而不用关心对方是同进程的另一个线程、隔壁进程、还是三米外机柜里的另一块板子。

这正是第 1.4 节说"Rust 在中间件层最有优势"的原因：中间件是并发的、长期运行的、一旦崩了满盘皆输的基础设施，恰好是 Rust 的所有权与无畏并发最能发力的地方。

三种通信模式：pub/sub、服务、动作

不同的模块交互，语义不一样。中间件通常提供三种模式，你要能分清什么时候用哪个。

1. 发布/订阅（publish/subscribe，pub/sub）

最核心、用得最多。 一个节点往一个具名的话题（topic）上发消息，任意多个节点订阅这个话题就能收到。发布者不知道也不关心谁在听——这叫解耦（decoupling）。

                       ┌──────────────┐
   /obstacles  ───────▶│  预测节点     │
   （感知发布）    │    └──────────────┘
                  ├───▶┌──────────────┐
                  │    │  规划节点     │
                  └───▶└──────────────┘
                       （还有个记录节点也在偷偷听，用于回放）

数据流是单向、异步、一对多的。感知每 100 ms 往 /obstacles 发一份障碍物列表，谁爱订谁订。这天然匹配传感器数据流：源源不断产生、多个下游消费、发的人不等收的人。自动驾驶里绝大多数数据（点云、图像、障碍物、定位结果、轨迹）都走 pub/sub。

2. 服务（service）：请求—应答

有时你要的是问一句、等一个答的同步语义。比如规划节点问地图节点："给我 (x, y) 附近 200 米的车道线"。这是一对一、双向、请求—应答（request/reply），语义上像一次远程函数调用（RPC）。

   规划节点  ──── 请求：附近车道 ────▶  地图服务节点
            ◀─── 应答：车道列表 ─────

服务不适合高频数据流（你不会每 10 ms 请求一次点云），适合偶发的、需要立刻拿到结果的查询。

3. 动作（action）：长任务 + 反馈 + 可取消

有些请求执行很久，比如"泊车入位""导航到某个点"。你既想要最终结果，又想要中途反馈（进度到 60% 了），还想能中途取消。这就是动作（action），可以理解成"带进度条和取消键的服务"。ROS 2 内置了这套语义（底层其实是几个话题 + 服务拼出来的）。

中高级视角：初学者容易把什么都做成服务（因为它像函数调用，最好懂）。工业界的经验法则反过来：优先用 pub/sub，除非你真的需要"等一个答复"。服务是同步的，一旦对端卡住，请求方就阻塞，容易在系统里制造级联卡顿。数据流一律 pub/sub，只有"查询配置""触发一次标定"这种才用服务。

进程内 vs 进程间 vs 跨机：延迟差几个数量级

"发一条消息"听起来一样，代价却天差地别。你必须对数量级有感觉，否则会写出把 2 MB 点云每帧序列化+拷贝三遍的灾难代码。

边界典型机制一次传递的量级关键代价
进程内（线程间）共享内存 / channel / Arc几十纳秒 ~ 微秒几乎只是移动一个指针
进程间（同机）共享内存 / Unix socket / loopback微秒 ~ 几百微秒可能要序列化 + 拷贝
跨机（网络）UDP / TCP / RDMA几百微秒 ~ 毫秒序列化 + 网络栈 + 物理链路

关键洞察有两个：

  1. 进程内传大数据几乎免费——只要你传的是"指向数据的指针/引用"而不是"数据的拷贝"。Rust 的 Arc<PointCloud>（原子引用计数）就是干这个的：多个线程共享同一份点云，谁都不拷贝。
  2. 一旦跨了进程，序列化（serialization）就成了主要开销。把内存里的 Vec<Obstacle> 变成一串可传输的字节（再在对端变回来），对 2 MB 点云，光这一步就可能吃掉几毫秒。所以才有了后面要重点讲的零拷贝共享内存——同机的两个进程直接读同一块物理内存，跳过"序列化+拷贝+反序列化"。

好的中间件会自动根据"收发双方在不在同一台机器/同一个进程"选最快的路径：同进程走共享指针，同机走共享内存，跨机才走网络。这叫透明的传输选择，是评价一个中间件是否成熟的重要指标。

一个 100 行的"迷你中间件"：把 pub/sub 讲成代码

概念说再多不如看一眼它长什么样。在真上 ROS 2 之前，我们用纯 Rust 的 channel 手搓一个进程内的 pub/sub，让你对"发布者不认识订阅者""一份数据多个消费者""大数据靠 Arc 零拷贝"这几件事有肌肉记忆。这段代码可直接编译运行（只依赖标准库）。

use std::collections::HashMap;
use std::sync::mpsc::{channel, Receiver, Sender};
use std::sync::{Arc, Mutex};
use std::thread;
use std::time::Duration;

/// 沿用第 1.3 节的 Obstacle（精简版）。
#[derive(Debug, Clone)]
struct Obstacle {
    id: u32,
    position: [f64; 3],
    velocity: [f64; 3],
}

/// 一帧感知输出。用 Arc 包起来：多个订阅者共享同一份，不拷贝——
/// 这就是"进程内传大数据几乎免费"的关键。
type ObstacleFrame = Arc<Vec<Obstacle>>;

/// 极简的话题总线：按话题名维护一组订阅者的发送端。
#[derive(Default)]
struct Bus {
    subscribers: Mutex<HashMap<String, Vec<Sender<ObstacleFrame>>>>,
}

impl Bus {
    /// 订阅一个话题，拿到一个接收端。发布者完全不知道谁调了它。
    fn subscribe(&self, topic: &str) -> Receiver<ObstacleFrame> {
        let (tx, rx) = channel();
        self.subscribers
            .lock()
            .unwrap()
            .entry(topic.to_string())
            .or_default()
            .push(tx);
        rx
    }

    /// 发布：把这一帧分发给该话题的所有订阅者。注意只 clone 了 Arc（引用计数+1），
    /// 底层那一大片障碍物数据一次都没被拷贝。
    fn publish(&self, topic: &str, frame: ObstacleFrame) {
        if let Some(subs) = self.subscribers.lock().unwrap().get(topic) {
            for tx in subs {
                let _ = tx.send(Arc::clone(&frame)); // 忽略"对端已退出"错误
            }
        }
    }
}

fn main() {
    let bus = Arc::new(Bus::default());

    // 两个订阅者：一个当"预测"，一个当"记录"。它们互不知道对方存在。
    let rx_pred = bus.subscribe("/obstacles");
    let rx_log = bus.subscribe("/obstacles");

    let h_pred = thread::spawn(move || {
        for frame in rx_pred {
            println!("[预测] 收到 {} 个障碍物，首个 id={}", frame.len(), frame[0].id);
        }
    });
    let h_log = thread::spawn(move || {
        for frame in rx_log {
            println!("[记录] 存档一帧，含 {} 个障碍物", frame.len());
        }
    });

    // 发布者：以 10 Hz 发 3 帧就收工。它调用 publish 时对订阅者一无所知。
    for seq in 0..3 {
        let frame: ObstacleFrame = Arc::new(vec![Obstacle {
            id: 42,
            position: [30.0, -1.5 + 0.03 * seq as f64, 0.0],
            velocity: [0.0, 0.3, 0.0],
        }]);
        bus.publish("/obstacles", frame);
        thread::sleep(Duration::from_millis(100));
    }

    // 丢弃 bus 让 channel 关闭，两个订阅线程随之结束。
    drop(bus);
    h_pred.join().unwrap();
    h_log.join().unwrap();
}

这 100 行里藏着中间件的全部灵魂：

  • 解耦：publish 里没有一个字提到"预测"或"记录"，发布者对订阅者一无所知。想加第三个订阅者（比如可视化），发布者代码一行不改。
  • 一对多：一次 publish，两个订阅者各收一份。
  • 零拷贝：分发时 Arc::clone 只是把引用计数加一，那片障碍物数据始终只有一份。把 Obstacle 换成 2 MB 点云，这段代码的开销几乎不变——这就是 8.3 要跨进程复刻的能力。

真正的中间件（ROS 2、Zenoh）无非是把这个 Bus 做到跨进程、跨机器，再加上序列化、发现、QoS、可靠重传。心智模型，就是这段代码。

车载中间件的四条硬需求

选型时你会反复听到这几个词，逐个说清它们到底指什么。

低延迟与确定性（determinism）

低延迟好懂——控制回路晚 10 ms 车就可能画龙。但确定性更重要也更容易被忽略：车载系统怕的不是"平均慢"，而是"偶尔特别慢"。一个平均 1 ms、但每 1000 次里有一次 50 ms 的中间件，比一个稳定 3 ms 的更危险——因为那次 50 ms 的**尾延迟（tail latency）**可能正好撞上一次紧急制动。

这就是为什么带 GC 的语言（Java、Go）在这层出局（GC 停顿破坏确定性），也是 Rust 的机会：没有 GC、无停顿、内存行为可预测。

零拷贝（zero-copy）

前面说了：跨进程的大数据，序列化+拷贝是主要开销。零拷贝的意思是数据从产生到消费，在内存里只存在一份，中间不发生拷贝。对 12 万点的点云、6 MB 的图像，这不是优化，是能不能实时的分水岭。实现方式通常是共享内存（shared memory），8.3 节会详细讲。

QoS：可靠性与时效性的显式权衡

QoS（Quality of Service，服务质量）是中间件让你**显式声明"这条数据流的传输策略"**的一组旋钮。最关键的两个维度：

  • 可靠性（reliability）：RELIABLE（可靠，丢了重传，像 TCP）还是 BEST_EFFORT（尽力而为，丢了就丢，像 UDP）。听起来当然要可靠，但——对 100 Hz 的点云，重传一帧 100 ms 前的旧点云毫无意义，你要的是最新的那帧，丢一帧无所谓。所以传感器流常用 BEST_EFFORT；而"急停指令"这种必须用 RELIABLE。
  • 历史/时效（history / durability）：只保留最新 N 条？还是要让晚加入的订阅者也能收到之前发的（durability，持久性）？地图、静态配置适合"晚来的也给"，实时点云适合"只要最新"。

面试题：为什么自动驾驶里传感器数据流经常故意用"不可靠（best-effort）"传输？ 答：因为传感器数据的价值随时间急剧衰减。一帧点云的意义在于"此刻世界的样子"，重传一帧几十毫秒前的旧数据不但没用，还会挤占带宽、增加延迟。对高频数据流，"永远拿到最新的一帧"比"一帧都不丢"重要得多。可靠传输留给低频、每条都关键的指令类消息。

除了这两个，QoS 通常还有 deadline（承诺多久发一次，超时报警）、liveliness（对端还活着吗）等——它们让中间件不只是"传数据"，还能帮你监控数据流健康。

计算图（computation graph）：把系统看成一张图

把上面所有东西合起来，你就得到自动驾驶软件的核心心智模型：计算图。

  • 节点（node） = 图的顶点 = 一个独立的处理单元（一个进程，或进程内一个可寻址的组件）。感知是一个节点，定位是一个节点，控制是一个节点。
  • 话题/服务 = 图的边 = 节点之间的数据流。

于是第一部分那个顺序的 autonomy_tick，真实形态是这样一张有向图：

  [相机驱动] ─/image─┐
                     ├─▶[感知]─/obstacles─┬─▶[预测]─/predictions─▶[规划]─/trajectory─▶[控制]─/cmd─▶[底盘]
  [激光驱动] ─/cloud─┘                    │                          ▲
  [IMU驱动]  ─/imu──▶[定位]─/ego_pose─────┴──────────────────────────┘
                        ▲
  [GNSS驱动] ─/gnss─────┘

每个方框是一个独立进程，各跑各的频率；每条边是一个话题。这张图有几个直接的工程好处：

  • 可观测：你能用工具（ROS 2 的 rqt_graph）把这张图画出来，一眼看到"谁在发、谁在收、哪条边断了"。调试分布式系统，能画图是巨大的优势。
  • 可录制回放：既然模块间只通过话题通信，你就能把所有话题的消息按时间戳录下来（rosbag / mcap），事后离线重放，复现任何一次路测中的问题。这是数据闭环的基石，第九部分会展开。
  • 可局部替换：想换个规划算法？只要新节点订阅 /predictions、发布 /trajectory，接口不变，图里的其他节点毫无感知。你甚至能把真实感知换成"仿真器发的假 /obstacles"来单独测试规划——这就是仿真在做的事。

真实项目里：你手边的 inf/ 就是这套思路在离线侧的体现。它是一条把 Python 推理流水线移植成 Rust 的数据处理管线，跑在数据闭环的离线推理/评测环节——路测录下来的数据，喂给这条 Rust 管线重新推理、算指标。虽然它不一定用 ROS，但"独立模块 + 明确的数据接口 + 可回放"的思想是一脉相承的。在线的车上是计算图，离线的机房里是数据管线，两者共享同一套"节点 + 消息"的世界观。

中间件语言/血统通信底层语义Rust 支持适用场景与现实
ROS 1C++/Python，学术界起家中心化 master + TCP/UDPpub/sub、服务、动作弱（社区绑定）已停止新特性、2025 EOL。有 master 单点、无实时/QoS、无内置安全。适合科研原型，量产不选。
ROS 2C++/Python 为主默认 DDS（可换 rmw）pub/sub、服务、动作社区 rclrs主流机器人框架。去中心化、有 QoS 与 SROS2；量产仍需结合平台做确定性、安全与维护评估。
DDS（如 Cyclone、Fast-DDS）C++，源自国防/航空UDP 多播，去中心化pub/sub（DDS 无原生服务）有绑定，非原生ROS 2 的默认底座。工业级、QoS 丰富、有认证。发现机制在大规模下较重，配置复杂。
ZenohRust 原生统一 pub/sub/query，自适应传输pub/sub、query、可做服务一流（本体就是 Rust）新一代，被选为 ROS 2 的 rmw_zenoh。轻量、能跨云-边-端、低带宽下更优。生态比 DDS 年轻但增长快。8.3 节重点。
Apollo CyberRTC++，百度为自动驾驶自研共享内存 + 协程调度计算图 + 有向无环调度无官方 Rust专为自动驾驶设计，面向确定性调度（不只是通信，还管任务调度）。绑定 Apollo 生态。
自研各家自选通常共享内存 + 自定义协议按需看团队头部车企/自动驾驶公司常有。为极致性能与确定性、去掉不需要的通用性。成本高、只有规模够大才划算。

几条帮你决策的大实话：

  • 从 ROS 2 起步几乎总是对的——除非你有极强的理由。它把 pub/sub、服务、动作、QoS、录制、可视化、安全一整套给你了，社区和工具最全。学它就是学这个领域的通用语言。
  • DDS vs Zenoh 是 ROS 2 底层之争。DDS 成熟、有认证背书；Zenoh 更轻、更适合"车-路-云"这种跨网络拓扑，且是 Rust 写的。ROS 2 官方推 rmw_zenoh 正是看中后者。8.3 节详谈何时选谁。
  • CyberRT 和自研的共同点是：它们不满足于"通用中间件"，而是把调度也管起来——精确控制每个任务在哪个核、什么时候跑，追求硬确定性。这是通用中间件（为了通用而牺牲一点极致确定性）和专用框架的根本张力。你在头部公司会遇到自研，但面试和入门，吃透 ROS 2 + DDS/Zenoh 是性价比最高的。

小结

  • 模块做成独立进程/节点、用消息通信，是为了解决频率打架、故障隔离、独立迭代、跨机部署——中间件就是承担这层通信的基础设施。
  • 三种通信模式：pub/sub（解耦的一对多数据流，用得最多）、服务（请求—应答）、动作（带反馈可取消的长任务）。数据流优先 pub/sub。
  • 通信跨越进程内/进程间/跨机三种边界，延迟差几个数量级；跨进程时序列化是主要开销，故有零拷贝共享内存。
  • 车载四条硬需求：低延迟、确定性（怕尾延迟）、零拷贝、QoS（可靠性/时效性的显式权衡）。传感器流常用 best-effort。
  • 系统的心智模型是计算图：节点是顶点、话题是边；它带来可观测、可回放、可局部替换三大工程红利。
  • 选型：ROS 2 是主流起点，其底层在 DDS（成熟）与 Zenoh（Rust 原生、下一代）之间；CyberRT/自研把调度也管起来追求硬确定性，但成本高。
